## 2. 三个概念，别混

| 名字 | 是什么 | 存哪 |
|---|---|---|
| **活动时区** | 「这个时间是按哪儿的钟说的」——**输入时的解释** | `activities.timezone`（IANA 名） |
| **我的时区** | 「我希望按哪儿的钟看」 | `user_prefs.timezone`；没设则**跟随浏览器** |
| **设备时区** | 浏览器报的 | `Intl.DateTimeFormat().resolvedOptions().timeZone` |

存储一律 UTC（`timestamptz`），三者都只影响**解释与呈现**。

⚠★活动时区不是「谁建的会他在哪」★：「我在纽约给北京的组会排 15:00」——指的是**北京时间 15:00**。
所以它是一个**显式的输入选项**，不能拿创建者的时区自动填死。

## 3. 实施顺序（每一步自己能站住，不依赖后面）

### 步骤 1 ★先把 57 处收敛成一处★（不改任何行为）

新建 `web/src/tz.ts`：

```ts
export function setMyTz(tz: string | null): void      // 应用启动读完 /api/me/prefs 调一次
export function myTz(): string                        // 设置优先，没设则浏览器
export function fmtHM(t: string | Date, tz?: string): string      // 15:00
export function fmtDay(t: string | Date, tz?: string): string     // 8/12 周三
export function fmtRange(a, b, tz?: string): string               // 15:00–16:30
export function inTz(t: string | Date, tz: string): Date          // 用于布局计算
```

底层一律 `Intl.DateTimeFormat(zh-CN, { timeZone })`，**不自己算偏移**
（夏令时、历史时区变更都不是我们该重新实现的东西）。

把 8 个文件里的调用逐个换成它（含 4 份复制的 fmtDay/fmtHM）。★这一步做完，行为完全不变★
（`myTz()` 在没设置时返回浏览器时区，与今天等价），
但从此「时间怎么渲染」只有一处推导 —— 后面两步才有地方落。

⚠ 布局计算（`schedule-layout.ts` 把活动摆进网格）也必须走同一处：
它算的是「这场会在**哪一天的第几行**」，用错时区会让活动**摆到错误的那一格**，
而不只是文字显示错——这是比文案更难发现的一类错。

### 步骤 2 E0：设备时区 ≠ 我的时区 → 提示条

日程页顶部一条可关闭的提示：
「你的设备时区是 America/New_York，当前按 Asia/Shanghai 显示。去设置切换？」

- 只有**两者不一致且用户显式设过** `user_prefs.timezone` 时才出现
  （没设过的人 `myTz()` 就是浏览器时区，永远一致，不会被打扰）；
- 关闭状态存 `localStorage`，★按「设备时区 + 设置时区」这对组合记★ ——
  换个地方出差再打开，应该重新提示一次，而不是因为上次关过就永远不提了。

### 步骤 3 E1：发起表单加「活动时区」

- 默认值 = `myTz()`；
- ★关键不是那个下拉，是换算★：表单里填的是**墙上时间**（15:00），
  提交时必须按**所选活动时区**解释成 UTC 瞬时。
  今天的代码是 `v.range[0].toISOString()` —— 那是按**浏览器**解释的。
  选了「北京」而人在纽约时，两者差 12–13 小时，**而且不会报错**。
- 详情页「改时间」同理。

### 步骤 4 E2：跨时区才标注

渲染时间的地方，若 `activity.timezone` 与 `myTz()` **不同**，在时间后补「（北京 15:00）」。
一致则一个字都不加（国内 99% 的情况看不到任何多余的字）。

判据只写在 `tz.ts` 里一处，供各视图调用。

### 步骤 5 后端四处写死东八区 → 真时区

⚠★这一节实现时改过两次，最终结论与初稿不同，以这里为准★：

| 位置 | 跟谁走 | 为什么 |
|---|---|---|
| `notify.rs`（8 个 `fmt_when` 调用点） | **活动自己的** + 标注 | 一条正文发给 N 个人；且站内信是**存下来的记录**，按收件人渲染会随他改时区而过期 |
| `remind.rs` | **活动自己的** + 标注 | 2026-08-12 liaoruili「统一！」——原本按收件人且不标，与上一行是两套规则，读的人分不出哪条按谁的钟 |
| `projects.rs` | **操作者** | 归档被拒的报错是给当场那个人看的即时反馈，不是记录 |
| `items.rs` | **活动自己的** | ★它不是显示，是存进 `items.name` 的文件夹名★——名字一建好就固定，「跟着谁走」这问题本身不成立 |

★统一后的一句话规则：**消息里的绝对时刻一律按活动自己的时区说，并标出是哪个钟**。★
代价：海外用户仍要自己换算一次。但「将于 15 分钟后开始」这半句本来就是**相对**的、对谁都对，
急不急由它承担；括号里那个绝对时刻只要标明是哪个钟就不会误导。

## 6. 不做什么

- **不做浏览器自动探测改设置**（PRD E0 明确：手动设，只给提示条）；
- **不引第三方时区库**（`Intl` 够用；luxon/date-fns-tz 是几十 KB 的依赖，换来的只是语法糖）；
- **不改存储**：一律 UTC，这条不动摇。

## 7. 开放问题 ★2026-08-12 三条全部关闭（liaoruili 拍板）★

### ① 时区在界面上叫什么名字

E2 的例子写的是「（**北京** 15:00）」，但库里存的是 `Asia/Shanghai`。

- **甲**：维护一张小的中文名映射（北京 / 纽约 / 伦敦 / 东京…），映射不到就显示 IANA 名。
  好处是读起来自然，代价是这张表要有人维护，且「Asia/Shanghai 该叫北京还是上海」是个会被吵的问题。
- **乙**：一律显示 IANA 名「（Asia/Shanghai 15:00）」。零维护、零歧义，但不像人话。
- **丙**：用 `Intl` 的 `timeZoneName: 'short'` → 「（GMT+8 15:00）」。零维护，但 GMT+8 不告诉人那是哪儿。

**我倾向甲**，只收十来个常见的，其余落回乙 —— 因为这句话存在的**全部意义**就是让人一眼懂，
而「Asia/Shanghai」对非技术用户不构成解释。

> ★结论：甲（中文名映射）★ —— liaoruili 2026-08-12。

### ② 没设过时区的人，发起活动时「活动时区」默认填什么

- **甲**：填浏览器时区（他在哪就按哪儿算，符合直觉）；
- **乙**：填北京（国内绝大多数场景，且与今天的行为一致）。

**我倾向甲**：E0 已经决定「不设默认北京」，这里再默认北京就自相矛盾。

> ★结论：甲（跟随浏览器）★ —— liaoruili 2026-08-12。

### ③ 提示条关掉之后

- **甲**：按「设备时区 + 设置时区」这对组合记住，换组合再提示（我在 §3 步骤 2 里假设的就是这个）；
- **乙**：永久关闭，除非用户去设置里改。

**我倾向甲**：出差换地方是这条提示**最该出现**的时刻，而乙恰好在那时闭嘴。

> ★结论：甲（按「设备时区 + 设置时区」这对组合记）★ —— liaoruili 2026-08-12。

## 8. 风险

| 风险 | 应对 |
|---|---|
| ★渲染点改漏一处★，某个视图默默显示错时间 | 步骤 1 先收敛再改行为；改完 grep 全树确认没有裸 `new Date(...starts_at)` 残留，并考虑加一道机械门禁 |
| 布局计算用错时区 → 活动**摆错格子** | 布局与文案共用同一处推导；测试计划 #13 专门验它 |
| 夏令时 | 一律 `Intl` + IANA 名，不存偏移；测试计划 #4 钉住 |
| 后端批量查时区拖慢提醒循环 | 一次 `IN` 查询取全，不在循环里查 |
