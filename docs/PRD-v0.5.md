## 0. 背景与目标

### 0.1 这一版要解决什么

v0.4 做完了「会议协同」：约会、应答、忙闲、材料、纪要。
但它把自己框死在**会议**这一件事上，而用户真正想要的是**记录自己的时间都花在哪了**——
读文献、跑数据、写作、开会、看病、健身。会议只是其中一类。

**v0.5 的一句话目标**：让「汇流」从一个开会工具，变成**一个人一整天的时间记录与协作平台**。

### 0.2 目标

1. **活动模型泛化**：会议降级为「活动的一种类型」，类型可自建（A 节）；
2. **能记录，不只是能安排**：支持补录过去、支持提醒（F 节）；
3. **时间看得清**：日历压缩空白时段、身份一眼可辨、跨时区不出错（C/D/E/G 节）；
4. **归档不等于消失**：结题项目的历史照样在日程和统计里（B 节）。

### 0.3 ★非目标★（这一版明确不做）

写清非目标是为了**防止范围蔓延**——下面每一条都是有人可能提、而我们这一版决定不做的：

| 不做 | 为什么 |
|---|---|
| **浏览器桌面通知 / 邮件提醒** | 真后台推送要 Service Worker + VAPID；邮件要平台通道。这一版靠站内信 + 页面弹窗（F2），**已知代价：人不在电脑前会错过** |
| **自建类型带参与人/纪要能力** | 会把「输个名字就能用」变成「填一张表」（A3） |
| **跨人共享自建类型 / 团队类型字典** | 每人一套（A2），团队统一口径这一版不做 |
| **移动端 App / 小程序** | Web 响应式即可 |
| **日历双向同步（订阅进来、写回 Google Calendar 等）** | 只出不进的 `.ics` 导出可以考虑，双向同步是一致性泥潭 |
| **AI 自动识别活动类型 / 自动填时长** | 记录的准确性比省那两下点击重要 |
| **多人共享的「团队日历」视图** | 忙闲查询已覆盖「他什么时候有空」这个真需求 |

### 0.4 成功判据

一个人用两周之后，**他自己的日程页是满的**——不是因为他被拉进了很多会，
而是因为他把自己做的事记了进去；并且他能说出「我这两周有多少时间花在 X 上」。

## 1. 角色

沿用 v0.4，无变化：

| 角色 | 是什么 |
|---|---|
| **超管** | 平台白名单（`CONGROVE_SUPER_USERS`），跨项目可见，用于救火与治理 |
| **项目主持人（owner）** | 每个项目唯一；可归档/删除项目、转移主持人（需对方接受） |
| **项目管理员（admin）** | 可加人、改设置 |
| **项目成员（editor）** | 可写内容、发起活动 |
| **只读成员（viewer）** | 只能看 |
| **活动发起人 / 记录员 / 参与人 / 旁听者** | 活动内的身份，★不携带任何资料权限★（资料权限只来自项目成员身份） |

## 2. 概念模型

```
用户 ──┬─ 属于多个 项目（角色:viewer/editor/admin，owner 唯一）
       │
       ├─ 拥有自己的 活动类型（自建，每人一套 + 系统预置两种）
       │
       └─ 参与/发起 活动 ──┬─ 有一个 类型（决定它有哪些能力）
                            ├─ 关联 0..N 个 项目（会议必须 ≥1；个人记录可以 0）
                            ├─ 有 0..N 个 参与人（所有类型都可以；★过去的活动不发通知★）
                            ├─ 有 0..1 份 纪要（仅当类型 has_minutes）
                            └─ 有 0..N 份 材料/录制（所有类型都可以）
```

**两条贯穿全局的规则**（从 v0.4 继承，仍然成立）：

1. ★**资料权限的唯一来源是「当前项目成员身份」**★（原 D3）——
   参与一场活动**不给**任何资料权限；离开项目即失去全部，含他参与过的活动。
   因此绝不能加「授权生效时间」这类字段。
2. ★**一个活动可以关联多个项目，材料整份进每个关联项目**★（原 D4）。

## A. 活动模型（原「会议」）★2026-08-07 已确认★

### A0. 「会议」重构为「活动」，会议成为活动的一种类型

**为什么**：下一版要让用户**记录每天的日程**——读文献、跑数据、写作、看病、健身。
叫「会议」就把这件事框死了：大部分日程根本不是会。
**活动**是那个更大的容器，**会议只是其中一种类型**。

这不是改名。真正的问题是：现在的硬约束**大多只对会议成立**——

| 现有硬约束 | 对「会议」 | 对「下午去医院」 |
|---|---|---|
| 记录员必填（D14） | 合理 | 荒谬 |
| 必须关联至少一个项目（D3 材料权限来源） | 合理 | 别扭：难道为「跑步」建个项目 |
| 参与人 / 应答 / 忙闲 / 纪要 / 录制转写 | 合理 | 全都用不上 |

### A1. ★类型决定能力，不是纯标签★

类型带一组**能力位**，一个活动要校验什么、详情页出不出纪要区，**全部从类型推导**。

★2026-08-07 精简：能力位只剩三个★

| 能力位 | 会议 | 个人日程 | 用户自建 |
|---|---|---|---|
| `has_minutes` 纪要与记录员 | ✅ | ❌ | ❌ |
| `needs_project` 必须关联项目 | ✅ | ❌ | ❌ |
| `busy` 产生忙闲 | ✅ | 用户可改 | **用户可改** |

**参与人 / 材料 / 补录对所有类型统一开放**——
★一个字段用不用是用户的事，不是类型替他决定的★：
读书会也可能是几个人一起读，「跑数据」也可能想挂一份脚本。

被砍掉的三个能力位各有理由：

| 砍掉 | 为什么 |
|---|---|
| ~~`has_participants`~~ | 参与人**统一**（L0）：判据不是类型，而是**时间过没过**——过去的不发通知 |
| ~~`has_materials`~~ | J0 已定个人活动也能传材料（落「我的活动材料」），这个位自相矛盾 |
| ~~`allow_past`~~ | 同上，所有类型都能填任意时间，只是过去的不发通知 |

**为什么留下的三个不能做成纯标签**：它们各自都有**硬后果**——
`has_minutes` 决定「记录员是不是必填」、`needs_project` 决定「材料有没有权限归属（D3）」、
`busy` 决定「别人看不看得到你忙」。★纯标签意味着这三条校验全都做不了★，
而 UI 只能写 `if (type === '会议')`，新增一个类型就要改代码。

### A2. 自建类型：★每人一套★

我建的类型只有我自己看得到。

- **个人日程本来就是私事**——你的「摸鱼」不该出现在别人的下拉里，也不该被别人改名/删掉；
- 代价是团队想统一口径（都叫「读文献」）做不到。**接受这个代价**：
  跨人统计本来就该按「活动类型名」这种软口径聚合，而不是靠强制共享一套字典。

### A3. 自建类型★只开一个开关：占不占忙闲★

自建 = 输一个名字就能用，**不需要理解任何概念**。
唯一的开关是「占不占忙闲」——因为**那是唯一真正影响别人的属性**：
它决定别人约你时看不看得到你这段时间是忙的。

参与人 / 纪要 / 材料这些能力**不开放给自建**：带这些能力的类型由系统预置。
→ 推论：**「预置类型列表」就是「带参与人的类型」的完整集合**。

### A4. 不关联项目的活动：默认仅自己可见，可改公开

- 默认**仅自己**：内容（标题、备注）只有自己看得到；
  若类型勾了「占忙闲」，别人查我忙闲时只看到**一个无标题的时间块**，看不到是什么事。
  ★这与现在「私密项目」的规则一致★，只是不再需要为了记个人日程去建项目；
- 可改**公开**：给「我在做什么想让人知道」的场景留出口（公开后全平台可见）。

### A5. 系统只预置两种类型

| 预置类型 | 能力 |
|---|---|
| **会议** | 全能力（参与人 / 纪要 / 材料 / 必须关联项目 / 占忙闲） |
| **个人日程** | 简单型（只有标题、时间、备注；忙闲用户可改） |

**预置多了是替用户做决定**——不同课题组的分类习惯差别很大，
而下拉里用不上的项只会碍事。自建成本已经低到「输个名字」，不必替他们预设。

### A6. 命名映射（改名范围）

| 旧 | 新 |
|---|---|
| `meetings` | `activities` |
| `meeting_participants` / `meeting_projects` / `meeting_messages` / `meeting_minutes` / `meeting_link_history` / `meeting_reads` | `activity_*` |
| `items.meeting_id` | `items.activity_id` |
| `/api/meetings*` | `/api/activities*` |
| 界面「发起会议」 | 「新建活动」 |
| 界面「参会人」 | 「参与人」 |
| 「会议纪要」「记录员」「旁听」 | 保留原词，但**只在带对应能力的类型上出现** |

新增表：`activity_types`（含预置两行 + 每人自建的行）。

## B. 项目归档（推翻 D17 的一部分）★2026-08-07 已确认★

### B0. 归档项目的历史活动★照常出现在日程里★

**推翻 D17 的日历过滤**。当初我写的理由是「日历回答『我接下来要做什么』，
塞满已结题项目的历史会议会变成考古现场」——这个视角是片面的。

liaoruili 的视角：**日程也是「我做过什么」的记录**。
「有时候用户就想回顾之前的工作，看看满日程的很有成就感」——
归档不该让过去消失，那些时间是真的花掉了。

### B1. 显示但★淡化 + 「已归档」标记★

照常出现在日历里，但颜色更淡、带一个小标。

**为什么不做成完全一样**：归档项目是**只读**的（D17 的这一半仍然成立）——
不加区分的话，用户会点进去想传材料、想改时间，才发现动不了，
而界面事先没给任何提示。★标记是为了让「动不了」这件事在点进去之前就可见★。

### B2. ★有未开始的活动就不允许归档★

归档 = 做完了。如果还有排在未来的活动，那就是没做完 —— 直接拒绝归档，
要求先处理（取消它们，或等它们开完）。

★「未开始的活动」**不含已取消的**★（2026-08-07 确认）——
取消了就不算有安排，不该因为一条作废的记录卡住归档。

推论：**归档项目里不会存在「未来的活动」**，
所以「归档项目的活动要不要占忙闲」这个问题自然消失（历史活动不产生忙闲）。

⚠ **实现要注意的边界：跨项目的活动**。
A 项目想归档，却卡在一场**同时关联 A 和 B** 的会上，而那场会主要是 B 的事。
处置：★错误信息里列出是哪几场★，让用户自己决定——
他可以把 A 从那场会的关联项目里去掉，也可以直接取消它。
**不要静默跳过跨项目的活动**：那等于允许「项目归档了但它名下还有未来的会」。

### B3. 归档项目的活动★计入统计★

那是真实发生过的投入，不该因为项目结题就从「我今年花了多少时间」里消失。
★否则会出现一个荒谬的现象：项目一归档，你今年的工作量就凭空少了一大块★。

分项目列表里带「已归档」标记区分。

## C. 日程上的身份标识与 hover ★2026-08-07 已确认★

### C0. 日历块要标出「我在这场活动里是什么身份」

现在日历块只按**可见性 + 应答状态**着色（公开=青实框 / 私密=紫虚框 / 待应答=红），
看不出「这场是我张罗的」还是「我只是去听听」。

### C1. 标三种身份：★发起人 / 记录员 / 旁听★

| 身份 | 标 | 为什么 |
|---|---|---|
| 我发起的 | ✅ | 我要对它负责 |
| 我是记录员 | ✅ | ★唯一带「欠着一份活」的身份★——会后要整理纪要，在日历上看得到比事后被催强 |
| 我只是旁听 | ✅ | 与「参与」性质不同：不用答复、拿不到材料，标出来免得误以为自己是正式参会人 |
| 普通参与人 | ❌ **不标** | 默认状态不该占视觉。全标的话满屏都是同一个图标 = 等于没有图标，反而把真正特殊的那几个淹了 |

### C2. 形式：★标题前的小图标★（AntD 图标，不用 emoji）

发起=星标 / 记录员=笔 / 旁听=空心圈。

⚠ ★不用 emoji★：容器里没有 emoji 字体时会显示成豆腐块——
截图脚本已经踩过这个坑（`e2e/shot.mjs` 里有记录）。

不选「左侧竖色条」是因为**颜色不能自解释**，得靠图例记；
也不做「图标+色条双重编码」——一个 30px 的小块上堆颜色、边框、图标、标题四种信息，容易花。

### C3. hover 显示：完整标题 + 时间 + 所属项目 + 我的身份

★标题必须在里面★：块小的时候标题常被截成「模型评…」，
**hover 是看全它的唯一机会**——如果 tooltip 里只放项目，那被截断的标题就永远看不全了。

不放参与人数/地点/链接：tooltip 一大就会遮住相邻的时间格，
而那些信息点进去就有。

## D. 日历时段收缩 ★2026-08-07 已确认★

### D0. 凌晨 0–8 点压缩成 ★2 小时一格★

那段时间基本没人安排，却占掉日历近三分之一的高度。

### D1. 压缩区里有活动时★照样压缩，块变矮★

不做「有活动就自动展开」——整周行高统一，布局简单可预期。

⚠ **代价与缓解**：一个 1 小时的活动在 2h/格 的区域里只有 ~15px 高，点不中也读不出。
所以实现上给压缩区的块一个**最小高度保底（≈18px）**，
并依赖 C3 的 hover（完整标题 + 时间 + 项目 + 身份）把看不清的信息补回来。
★这里「块高 = 时长」的视觉契约本来就已经被压缩打破了★，保底不再多破坏什么。

### D2. 晚上★不收缩★，保持压暗

★凌晨和晚上不是一回事★：前者几乎没人安排，后者只是不在工作时间——
晚餐会、跨时区的会、自己晚上写东西都真实存在。

## E. 时区 ★2026-08-07 已确认★

### E0. 用户在设置里设当地时区，★不设默认北京★

不做浏览器自动探测。

⚠ **已知代价**：没设过的海外用户会看到全错的时间，而他未必意识到要去设置里改。
**缓解（实现时做）**：检测到浏览器时区与设置不一致时，在日程页顶上给一条**可关闭的提示条**——
「你的设备时区是 America/New_York，当前按 Asia/Shanghai 显示，去切换？」
★这不违背「手动设」这个决定★，只是让用户知道有这回事，而不是默默看错时间。

### E1. 建活动时可选**这场活动的时区**，显示时自动换算成看的人的时区

- 存储一律 UTC（`timestamptz`），时区名（IANA，如 `Asia/Shanghai`）单独存一列；
- 活动的时区是**输入时的解释**：「我在纽约给北京的组会排 15:00」——指的是北京时间 15:00；
- ★也是周期规则展开的基准★：「每周三 15:00 北京时间」跨夏令时不会整体漂一小时
  （这正是数据模型里坚持存 IANA 名而不是固定偏移的原因）。

### E2. ★跨时区时才标注原始时区★

活动时区与我的设置一致 → 不标（国内用户 99% 的情况看不到任何多余的字）；
不一致 → 时间后面补一句「（北京 15:00）」。

**为什么必须标**：跨时区的人看到「凌晨 3:00」会懵——
不知道这是对方的下午，还是真要自己凌晨爬起来。★那个数字必须有个解释★。

## F. 补录与提醒 ★2026-08-07 已确认★

### F0. ★所有类型都能填任意时间★（`allow_past` 能力位已废弃）

原本打算按类型区分「能不能排过去的时间」，后来发现**不需要**（见 L0）：

> **所有活动都能填任意时间；过去的不发通知。**

- 补录一场临时会（用「会议」类型、时间填昨天）→ 允许，不发通知；
- 「昨天下午改论文改了 3 小时」→ 允许，不发通知。

★原来那条「会议不能排过去的时间」的校验去掉★——
它当初是为了防「约一个已经过去的会」的误操作，
但**补录一场已经发生的会是正当的**，而误操作由 F1 的「超 7 天确认」兜住。

### F1. 补录不限时间，但★过久的给个确认★

想补多久以前的都行——**这是自己的记录，不是报销**，
回头整理上个月做了什么是正当需求，加硬限制只会挡住真实用法。

★超过 **7 天** 就确认★（2026-08-07 liaoruili 定，我原本提的 90 天太松）：
弹一句「这是 7 月 28 日的，确认吗？」。

**为什么 7 天而不是 90 天**：真实的补录多半是「昨天/前天忘了记」——
一周之内。跨过一周还在补，就已经值得停下来看一眼日期对不对了。
90 天那个阈值太松，等于这道闸只挡得住「输错年份」这一种错，
而**输错月份、输错日期**才是更常见的手滑。

### F2. 提醒：★站内信 + 页面内弹窗★

- **站内信**是现成的（平台 registry，汇流已在用），不需要新基建；
- 页面开着时额外弹一个提醒框。

★不做浏览器桌面通知 / 邮件★：桌面通知关了页面就收不到（真后台推送要
Service Worker + VAPID，工作量大得多）；邮件要先确认平台有没有可用通道。
**已知代价：人不在电脑前就真错过了。** 这一版接受。

### F3. 提醒时长：★个人全局默认 + 单个活动可改★

设置里定一个默认（如提前 15 分钟），建/改活动时可以单独改这一场。
**和手机日历一样，人不用学**；又能给「要开车去的那场会」单独设提前 1 小时。

可选值：不提醒 / 5 分 / 15 分 / 30 分 / 1 小时 / 1 天 / 自定义。

⚠ **补录的活动不发提醒**（时间已经过去了，提醒它没有意义）——
实现时要显式跳过，否则批量补录会一次炸出一堆无意义的站内信。

## G. 时间输入的手感（参考腾讯会议）★2026-08-07 已确认★

### G0. 开始时间默认当前时间，★取不取整按类型分★

| 类型 | 默认值 | 为什么 |
|---|---|---|
| 会议 | 向上取整到下一个 **15 分钟**（15:37 → 15:45） | ★没人约 15:37 开始的会★；参会人看到这种时间会以为发起人填错了 |
| 个人记录 / 自建 | **就用 15:37** | 那是「我刚做完，现在记」的真实时刻，取整反而要人手动改回去 |

与 A1（类型决定行为）一致：**同一个控件，行为由类型推导，不写死**。

### G1. 结束时间给★持续时长快捷选项★

不再只有一个绝对时间选择器。可选：**15 分 / 30 分 / 1 小时 / 1.5 小时 / 2 小时 / 3 小时 / 自定义**，
默认 **1 小时**。

★两者双向绑定★：
- 选「1 小时」→ 结束时间自动算出来；
- 直接改结束时间 → 时长下拉跟着显示成对应值（不在预设里就显示「自定义」）。

**为什么值得做**：绝大多数活动的时长是那几个常用值，
而「选一个绝对的结束时刻」要人在脑子里做一次加法——
★加法本身不难，难的是它出现在每一次创建里★。

⚠ 跨天的活动（如「出差 3 天」）走「自定义」，快捷选项只覆盖小时级。

## J. 「我的活动材料」与命名 ★2026-08-07 已确认★

### J0. 不关联项目的个人活动★也能传材料★

推翻我原来提的「不能传」。材料要落到某个项目才有权限归属（D3），
所以给每人一个系统默认的存档区：**「我的活动材料」**。

### J0b. 结构：★按「日期 + 活动名」分组★，要改就回活动去改

```
我的活动材料/
  2026-08-08 读文献 Acemoglu 2024/
    acemoglu-2024.pdf
    我的批注.md
  2026-08-07 田野访谈/
    录音.m4a
  2026-08-05 健身/
```

**任何更改都回到那条活动去做**——改名、删除、加材料，入口都在活动详情页。
这个区只是「把散落在各条个人活动里的东西汇到一处看」。

#### ★实现要点：这些「文件夹」是虚拟分组，不是真实目录★

材料的 `items` 行直接挂在「我的活动材料」项目下（`parent_id = NULL`），
前端**按 `activity_id` 分组**渲染成文件夹的样子。

为什么这样更干净（三个问题一次消失）：

| 如果做成真实目录 | 虚拟分组 |
|---|---|
| 活动改名 → 要同步改文件夹名（漏了就对不上） | 显示名直接读活动，**永远一致，零同步成本** |
| 要挡住「用户自己建文件夹 / 移动文件」 | **根本没有目录可建**，约束天然成立 |
| 同一天两个同名活动 → 文件夹重名要加序号 | 按 `activity_id` 分组，重名无所谓 |

排序按日期**倒序**（最近的在上）——这个区是用来回看的。

### J1. 它★不是一个项目★，只是技术上复用了项目表

| | 普通项目 | 我的活动材料 |
|---|---|---|
| 拉成员 / 授权 | ✅ | ❌ 只有我 |
| 建文件夹 / 在线编辑 / 版本历史 | ✅ | ❌ **什么都不能做** |
| 归档 / 删除项目 | ✅ | ❌ 系统建的，不能删 |
| 出现在项目列表里 | ✅ | ❌ 只在个人面板与活动详情里作为材料落点 |
| **复制到其他项目** | — | ✅ 这是它唯一的出口 |

**定位**：它是「个人活动产生的东西的存放处」，不是第二个工作区。
要拿去协作，就复制到真正的项目里。

### J1b. 删除：★删掉活动时连带删材料★

「我的活动材料」里**没有单独的删除入口**——材料始终依附于活动，
要删就删那条活动，它的材料跟着走（进回收站，30 天）。

概念上最干净：★这个区里的每一份材料都有主人（某条活动）★，不存在游离的文件。

⚠ **三条必须写清、否则实现会一刀切的边界**：

1. ★这条规则**只适用于「我的活动材料」**★。普通项目里删掉活动，
   **材料留在项目里**——那是项目的资产，不该被一次活动的删除带走
   （原 D10「会议材料进项目树的只读会议区」的精神）；
2. **已复制到别的项目的副本不受影响**：副本是独立的 items 行，
   引用计数保证底层 blob 不被误删。★这一点要在界面上说出来★，
   否则用户不敢删任何东西——「删了会不会把我复制到课题组那份也删了」；
3. UI 上要**说清没有单独删除入口**，否则用户找不到删除按钮会以为是 bug。

### J2. 跨项目复制：★实现上几乎免费★

v0.4 已有内容寻址去重（`blobs/<sha256>` + 引用计数），
复制 = 在目标项目建一行 items 指向**同一个 blob**，存储一个字节都不增加（「秒传」用的就是这套）。

三条要处理的：
- 需要**目标项目的 editor 权限**（复制是往目标项目里写）；
- 复制后是**独立副本**：改名 / 删除互不影响（引用计数保证 blob 不被误删）；
- ★配额按逻辑大小各算一份★——否则「谁先传谁倒霉」，而且用户无法理解自己项目的配额为什么被别人的文件占了。

### J3. 「项目」这个词★不改★

考虑过改回「空间」或改成「工作区」，结论是不改：

★**归档 = 做完了**（B2）——会归档、有始有终，这正是「项目」的含义★。
「空间」不会「做完」，给它一个归档按钮是自相矛盾的。

「项目装不下的东西」在新模型里各有出路，只是落点不在这里：

| 我想表达 | 落在哪 |
|---|---|
| 这件事**性质**是什么（读文献 / 健身 / 开会） | **活动类型**（A 节） |
| 这件事属于哪个**协作单元**（课题组 / 某篇论文） | **项目** |
| 纯粹是我自己的事 | 不关联项目，材料落「我的活动材料」 |

→ 「健身」不是一个项目，它是一个**活动类型**；
按类型统计「我这季度健身 20 小时」正是 A0 想要的。

### J4. 日程图例改成★公开 / 不公开★，去掉「项目」二字

判据从**项目的可见性**换成**活动自己的可见性**。

**为什么这是对的**：活动现在可以不关联任何项目（A4），
「只关联了私密项目」这个判据对它根本不适用——它连项目都没有。

★副产品：`is_private` 这个字段整个消失★——不必再从关联项目反推。
（那正是 v0.4 踩过「字段声明了但 SQL 没算，`#[sqlx(default)]` 静静给 false」的地方。
判据少一层推导，就少一处能悄悄错掉的地方。）

⚠ **注意「不公开」内部其实有两档**，但日历上不必区分（对我而言都是「别人看不到」）：
- 活动 `visibility=private` 且有参与人 → **参与人可见**；
- 不关联项目的个人活动 → **仅自己可见**。

## L. 类型的生命周期与配额 ★2026-08-07 已确认★

### L0. ★发不发通知，只看时间过没过★

**问题**（故事地图 §5 问题 1 查出来的）：昨天张三来找我聊了两小时，
今天我想记下来**并记上张三**——统计时我想知道和谁花了时间。

**决策**（liaoruili 2026-08-07 原话：「就参与人；复用之前的呀，只是不发通知而已，
已经过了的就不发通知，这样不就全部统一了吗」）：

> ★**参与人就是参与人，一套机制**★。
> **唯一的判据是活动开始时间过没过**：
> - 时间在**未来** → 照常发邀请、进对方日历、要应答；
> - 时间在**过去** → **不发任何通知**，纯粹是我这边的一笔记录。

⚠ 我原本的设计（`status='noted'` 新状态 + 「一起的人」这个新词）**已废弃**——
那是把简单的事复杂化了：造了一个新状态、一个新概念、还要在两处维护它们的差别，
而这一切用「时间过没过」一个判据就够了。

**推论**（都很自然，不需要额外规则）：
- 补录一场临时会 = 用「会议」类型、填过去的时间、填上参与人 → 不发通知；
- 补录一条个人记录带参与人 → 同样不发通知；
- ★对方的统计里不计入★：他从没答应过，也可能不知道你记了这一笔
  （统计只算「我参与且没拒绝」的，补录的活动对他而言连 pending 都没有）。

### L1. 活动类型★软删除★，历史照常显示

用户建了「读文献」、用了 20 次，然后想删掉它。

**决策**：类型行标 `deleted_at`——
- **历史活动照常显示它的类型名**（★统计不断档★）；
- 新建活动时不再出现在下拉里。

不做「删除时要求把历史转到别的类型」：那是把系统的问题丢给用户。

### L2. ★不提供「改类型」功能★——要改就删了重建

**为什么不做**：类型决定能力（A1），改类型意味着能力位变了——
会议改成个人日程，参与人往哪去？纪要留不留？
任何答案都是**静默丢数据**或**维护一张兼容矩阵**。

liaoruili 原话：「改类型相当于删除重建」。那就**如实呈现**：
不给这个按钮，用户想改就自己删掉重建。
★诚实的「不能做」好过一个会悄悄吃掉数据的「能做」★。

### L3. 配额★按用户算，不按项目★

**推翻 v0.4 的项目配额**（`projects.quota_bytes` 去掉）。

| | 旧（每项目 10GiB） | 新（★每用户 10GiB★） |
|---|---|---|
| 判据 | 这个项目里的东西加起来 | ★谁传的算谁的★，不管落在哪个项目 |
| 漏洞 | 建项目不花钱，一个人建 50 个项目就拿到 500G | 没有 —— 总量由人数决定 |
| 用户看到的 | 每个项目一个数，到处不一样 | 「我用了 3.2G / 10G」，**到处都一样** |

- 默认 10GiB，**超管可对单个人升降级**（原来的「改项目配额」改成「改用户配额」）；
- 归属人 = `items.created_by`；
- ★跨项目复制的副本按逻辑大小计入复制者★——
  物理上是同一个 blob（内容寻址去重），但用户理解的是「我的空间里有多少东西」；
  不算的话会出现「配额显示 0 但我有 100 个文件」这种没法解释的状态。

⚠ **「我的活动材料」不单列配额**，它和别的项目一样都吃用户的总额度。
但★它的页面上要显示用量条★——它不出现在项目列表里，用户没有别的地方能看到自己传了多少。

## K. 统计：★按类型★是主视角 ★2026-08-07 已确认★

活动泛化之后，「我这周开会 6h、读文献 12h、写作 8h」比
「AI 项目 8h、数据治理 6h」更接近人想知道的事 ——
**按项目分组回答「我为哪个团队花了时间」，按类型分组回答「我在做什么」**，

|---|---|
| **按类型**（新，主） | 我的时间都花在什么性质的事上 |

口径不变：**D5 三级回退**（录制 > 手工补录 > 排程），并显示口径来源。

按项目会重复计（一个活动可关联多个项目，D6「分组展开」）——
