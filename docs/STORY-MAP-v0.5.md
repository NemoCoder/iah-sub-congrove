## 0. 这份文档解决什么问题

PRD 是**按主题**组织的（活动模型、归档、时区、提醒…），
但人不是按主题用产品的——他是**沿着一条路走**的：进来、配置、记一笔、约个会、到点开会、事后回看。

故事地图把 PRD 摊到这条路上，用来回答两个问题：

1. **切到第几期时，用户能拿到一个完整的东西**（而不是一堆半成品）？
2. **这条路上有没有 PRD 没说到的坑**？——★这一节（§5）才是本文的真正产出★。

## 1. 骨干：一个人用汇流的一周

```
①配置自己 → ②记一笔 → ③约个会 → ④看日程 → ⑤到点开 → ⑥会后沉淀 → ⑦回看复用 → ⑧复盘统计
```

| 站 | 他在做什么 | PRD 里对应 |
|---|---|---|
| ① **配置自己** | 设时区、设默认提醒、建自己的活动类型 | E0 / F3 / A2·A3 |
| ② **记一笔** | 「我下午读了两小时文献」——选类型、填时间、可能补录 | A1 / F0·F1 / G |
| ③ **约个会** | 选人 → 看忙闲 → 发出去 → 收应答 / 处理改期 | H1（继承）/ 必参·选参 |
| ④ **看日程** | 一眼看出：哪些是我张罗的、哪些只是去听、哪些已归档 | C / D / B0·B1 / J4 |
| ⑤ **到点开** | 提醒响 → 点开 → 看到链接（跨时区能读懂） | F2·F3 / E2 |
| ⑥ **会后沉淀** | 传录制 → 自动转写 → 记录员整理纪要 | H1（继承）/ A1 的 `has_minutes` |
| ⑦ **回看复用** | 翻「我的活动材料」→ 把某份复制进课题组项目 | J0b / J2 |
| ⑧ **复盘统计** | 「我这季度开会多少、读文献多少」 | K / D5 口径 |

## 2. 切片原则

这一版是**重构**，所以切片有一条特殊约束：

> ★**数据库一次建好，不分期建表**★。库已清空、不走迁移，
> 分期加表等于自己给自己制造迁移。所以 M0 必须把 §I 的模型**一次建全**，
> 后面几期只填代码、不动 schema。

由此得到第一期是「**地基期**」——它对用户几乎不可见，但它让后面每一期都能独立上线。

## 5. ★故事地图查出来的问题★（PRD 没说，需要回填）

> 这是本文最该被认真读的一节。下面每一条都是**沿旅程走时撞到的**，
> 不定就会在实现时被随手决定掉。

### 问题 1 ★「补录一场临时会」走不通★ —— 与 F0 冲突

**场景**：昨天下午张三来找我，聊了两小时。今天我想把它记下来，
并且**记上「和张三」**——因为统计时我想知道和谁花了时间。

**冲突**：
- 「会议」类型 `allow_past=false`（F0）→ 补录不了；
- 「个人日程」类型 `has_participants=false`（A1）→ 记不上张三。

**这不是边缘场景**：临时讨论、走廊里聊、突然被叫去开会——**没提前排、事后才想记**是常态。

**候选处置**（需拍板）：
| 方案 | 说明 |
|---|---|
| A. 会议类型开放补录 | 把 `allow_past` 对会议也设 true。★但要防「补录一场会然后给别人发邀请」★——补录的会不发通知、不要应答 |
| B. 预置第三种类型「讨论」 | 有参与人、可补录、无纪要无材料。与 A5「只预置两种」冲突 |
| C. 参与人能力与补录解耦 | 补录时允许填参与人，但**只作记录不发邀请**（他们的日历上不出现） |

> ★**已拍板：C**★（2026-08-07）→ 写进 PRD **L0**。
> 补录的活动可以填参与人作为「谁在场」的记录，但**不发邀请、不进对方日历、不计对方统计**。

### 问题 2 ★活动类型删掉之后，用过它的活动怎么办★

用户建了「读文献」，用了 20 次，然后想删掉它。

**候选**：禁止删（只能改名）/ 软删除+历史照旧显示 / 删除时要求把历史转到别的类型。

> ★**已拍板：软删除**★ → PRD **L1**。历史照常显示类型名（统计不断档），新建时不再出现在下拉里。

### 问题 3 ★改活动的类型★——能力位变了，已有的数据怎么办

把一场「会议」改成「个人日程」：参与人、纪要、材料怎么办？

**候选**：禁止改类型 / 只允许在**能力位兼容**的类型间改（不丢数据）/ 允许改并提示将丢弃什么。

> ★**已拍板：不提供「改类型」功能**★（liaoruili：「改类型相当于删除重建」）→ PRD **L2**。
> 比我原来提的「只允许兼容方向」更干净：能力位差异带来的边界全都不存在，也不用维护兼容矩阵。
> ★诚实的「不能做」好过一个会悄悄吃掉数据的「能做」★。

### 问题 4 第一次登录时，那些「系统的东西」什么时候出现

`activity_types` 的两条预置行、每人的「我的活动材料」项目、`user_prefs` 默认行——
**什么时候创建**？PRD 没说。

> 我倾向 **登录时按需创建**（`auth.rs` 已有 upsert `app_user` 的位置，顺手做）：
> 不做「注册钩子」——平台侧的注册我们看不到；也不在建活动时才建，那会让第一次建活动变慢且容易并发。

### 问题 5 「我的活动材料」的配额是多少

> ★**已拍板，而且改法比我想的更根本**★：配额**从「每项目」改成「每用户」**（PRD **L3**）。
>
> liaoruili 原话：「每个用户一个 10G，而不是每个空间 10G，这样用户总量可以无限制」。
> ——★这同时补掉了一个我没看出来的洞★：建项目不花钱，
> 按项目算配额的话，一个人建 50 个项目就拿到 500G。按人算就没有这个口子。
>
> 「我的活动材料」因此不需要单列配额，它和别的项目一样吃用户总额度；
> 但它的页面上**要显示用量条**（它不在项目列表里，用户没别的地方能看到）。

### 问题 6 活动**必须**有类型吗

> 是。`type_id NOT NULL`，默认「个人日程」。
> ★不留「无类型」这个状态★：它会让所有按类型的统计出现一个叫「其他」的桶，
> 而那个桶只会越来越大。

## 7. 配额改动的影响面（实现时别漏）

★2026-08-08 口径改过一次★：从「按上传者 `created_by`」改成「**算项目 owner 的**」（PRD L3）。
下表已按最终口径重写。

| 位置 | 改成 |
|---|---|
| `projects.quota_bytes` | **删掉**（额度挂在人身上，不挂在项目上） |
| 新表 `user_quota` | 与 `user_prefs` **分开**：配额是超管授予的，不是用户偏好 |
| 上传前的配额预检 | 按 **项目 owner** 汇总他名下**所有项目**，不是按单个项目、也不是按上传者 |
| 超管面「改项目配额」 | 改成「**改用户配额**」 |
| 项目页的配额条 | 去掉；改成显示「本项目占了主持人 X GB」更有信息量 |
| 个人面板 / 我的活动材料页 | **新增**用量条「已用 3.2G / 10G」 |
| 回收站计不计入 | ★仍然计入★（占着盘就该算）——**这是全系统唯一刻意不带 `deleted_at IS NULL` 的读路径**，SQL 旁边必须写明，否则会被照着「反漂移纪律」改掉 |
| 跨项目复制的副本 | 计入**目标项目 owner** |
| 转移主持人 | 占用随之转移；★允许接手人超额★，超了只能删不能传（L3b） |
| 「超额」这个状态 | 判据统一成「已用 > 额度 → 一切新增写入拒绝、删除照常」——转移和超管调低额度都会造成它 |

★这个口径比「按上传者」实现更简单★：按 `project_id` 聚合（现有索引就有）再按 `owner` 汇总，
不需要 `items(created_by)` 索引，也不需要给 `item_versions` 加「这一版的作者」列。
