## 要守住的不变量（一句话）

> ★`blobs/<H>` 这个对象里的字节，哈希必须等于 `H`。★

整套内容寻址（去重、秒传、引用计数）全建立在这一句上。而它现在**不成立**。

## 它是怎么破的

三段代码单看都「有注释保护」，拼起来就漏：

| # | 位置 | 干了什么 |
|---|---|---|
| ① | `media.rs:170` | 预签名直传：`blobs/<客户端申报的 sha>` 不存在就**直接用它当 key**。申报值只校验了「64 位十六进制」这个形状 |
| ② | `media.rs:305` | complete 时 `multipart_complete` 落到那个 key —— S3 语义是**覆盖**。而 ① 的 `exists()` 发生在 **begin**，中间隔着 `PART_URL_TTL = 6 小时` |
| ③ | `items.rs:914` | 流式上传：「对象已存在就直接引用（哈希是我们自己算的，内容必然一致）」——★这个前提被 ① 打破了★ |

两条攻击路径，**都不需要并发**：

- **占位**：先 begin 申报别人文件的 sha=H（此时 `blobs/H` 不存在）→ 传任意字节 → complete。
  之后真正拥有该文件的人流式上传（服务端自算得 H）→ ③ 跳过复制、直接引用 →
  落成 `sha_verified=true` → 成为**合格秒传源**继续扩散。
- **覆盖（TOCTOU）**：begin 时 `blobs/H` 还不存在 → 占坑 → 等受害者传完把它建好 → 6 小时内 complete 覆盖掉。
  ★`media.rs:164` 那句「已存在则另起 `-<rand>` 绝不覆盖」只在 begin 那一刻成立。★

`verify_sha` 拦不住：它只把**攻击者自己那一行**的 `sha256` 改成真值，
**对象不动、不改名、不打标记**，也从不回头复验已经引用它的行。

净效果：★受害者上传的文件被静默替换，全链路 verified，无任何报错。★
这正是 `items.rs:35` 注释里点名要防的「百度那个凭哈希认领他人文件」的洞的**反向版本**。

## 决定

### D1 ★直传永远不落在规范 key 上★

`media::begin` 的 multipart 目标改成 `uploads/<iid>-<rand>`，**与申报的 sha 无关**。
申报的 sha 仍然记在 `items.sha256`（用于断点续传认领与秒传预检），但**不再参与 key 的推导**。

> 为什么这是根治而不是打补丁：不变量的形式是「谁能往 `blobs/*` 写」。
> 把答案收敛成**只有服务端算过哈希的路径**，① 和 ② 两条同时消失，
> 而且★以后新增任何上传路径都不会重新打开它★——除非它显式去写 `blobs/`。

### D2 归位（promote）只在服务端算完真实哈希之后

`verify_sha` 拿到真实哈希 `R` 之后：

1. `blobs/R` **已存在** → 直接把 `items.s3_key` 指过去，删掉临时对象（这就是去重，零拷贝）；
2. **不存在** → 服务端 copy 临时对象 → `blobs/R`，再指过去、删临时对象。

`sha_verified = true` **只在归位成功之后**置位。失败则保持 `false` +
`s3_key` 仍指临时对象 —— 文件能下载、但★不能当秒传源★（fail-closed）。

⚠ **归位的并发是良性的**：key 由**真实哈希**推导，所以两个并发归位要么写同一份字节、
要么根本不撞 key。不需要锁。

### D3 「申报值 ≠ 真值」要留下痕迹，不能改写成「已核验」

现状：`verify_sha` 发现不符只 `warn!`，然后照样 `SET sha_verified = true`
——★把「内容和客户端算的不一样」这个强信号，改写成「已核验」★。

而这个信号是有价值的：预签名 part 上没有任何 checksum（`storage.rs:7` 刻意压掉的，理由正当），
所以**任何保长度的传输损坏**（代理改写、坏内存、串片）都能通过 complete 的大小对账。
不符 = 很可能传坏了。

→ 加一列 `items.sha_declared_mismatch boolean NOT NULL DEFAULT false`；
前端在文件行上给一个「内容与上传端校验不符，建议重传」的提示。
**不阻止使用**（内容就是它自己，自洽），只是别假装一切正常。

### D4 已有的坏对象：不做数据修复

dev 库按 ADR-0001 每次部署清空；prod 通道还没开。**没有要修的存量**。
★prod 开出来之前必须合并本设计★，否则就要写一次性巡检脚本了。

## 不管什么

- 不引入对象级 checksum（`storage.rs:7` 的 `WhenRequired` 是踩过坑定下来的，别动）；
- 不做「引用同一 blob 的所有行回头复验」——D1 之后不再需要；
- 不改秒传的判据（`readable_blob` 只认 `sha_verified` + 逐行 `effective_role`，本身是对的，
  A2 是从**写**侧破坏它的前提，不是从它这里绕过）。

## ~~⚠ 一个必须先确认的实现风险~~ → ★已实测，风险关闭★（2026-08-09）

**结论先写：Garage 支持 `UploadPartCopy`（服务端分片复制），D2 的归位对多大的对象都成立。**

实测（对 dev 的 `s3api.ruciah.com`，脚本见 PR 描述）：12 MiB 源对象 → 3 个分片（5+5+2 MiB）
逐片 `UploadPartCopy` → complete → 取回比对 **逐字节一致**；单次 `CopyObject` 同样通过。

> ★验证方法本身值得记下来★（liaoruili 2026-08-09 纠正）：我原本写的是「必须先传一个 >5 GiB
> 的对象验 CopyObject 的天花板」——**把验证条件想复杂了**。
> 要验的不是「Garage 的天花板在哪」，是**「UploadPartCopy 这条码路通不通」**；
> 而 S3 的最小分片正好是 5 MiB，用一个 12 MiB 的对象跑 3 片，走的逻辑与 50 GB 完全相同。
> ★通了就是通了，天花板在哪不再是问题——因为根本不会去撞它。★
> 教训一般化：**要验的是自己那段代码的分支，不是依赖方的极限值**；
> 后者往往贵得多，而且验完还是别人的实现细节，随时会变。

### 由此定下的实现

```
promote(tmp_key, real_sha, size):
    dst = blobs/<real_sha>
    if exists(dst): 指过去，删 tmp        # 去重，零拷贝
    elif size <= COPY_SINGLE_MAX (4 GiB): copy_object(tmp → dst)
    else:                                  # 分片复制，已实测可行
        multipart copy，PART = 256 MiB（10000 片上限 → 支持到 ~2.4 TiB）
    指过去，删 tmp；置 sha_verified = true
```

阈值取 4 GiB 而不是贴着 5 GiB：留余量，且**这两条分支的行为必须一致**（都产出同一份字节），
所以阈值取多少不影响正确性，只影响走哪条路。

## ~~原风险描述（留作追溯）~~

`storage.rs:96` 的 `copy()` 用的是 **CopyObject**，而 S3 语义下 CopyObject 有 **5 GiB** 上限，
超过要走 **multipart copy**（UploadPartCopy）。而这个系统的主用例正是 **GB 级会议录屏**。

- 现状为什么没炸：流式上传那条路的 copy 走的是同一个函数，但 `items.rs` 的流式上传
  受入口层限制、实际不会有 5 GiB 的单次 POST；★而 D2 会让**直传的大文件**第一次走到这条 copy★。
- **必须先验**：Garage 的 CopyObject 对 >5 GiB 是拒绝还是照做。
  - 若拒绝 → `promote` 要实现 multipart copy（`UploadPartCopy` 分片，每片 ≤5 GiB）；
  - 或者**换个方向**：让 D2 的「不存在」分支**不复制**，而是把 `blobs/R` 做成
    「临时 key 的别名」——但 S3 没有别名，所以这条路走不通。
- 兜底方案（若 multipart copy 代价太大）：`blobs/` 下允许两类 key ——
  `blobs/<R>`（规范）与 `uploads/<iid>-<rand>`（大对象原地留下，只在 items 行上记 `sha_verified`），
  去重对超大对象降级为「不去重」。★这是可接受的：去重的收益在小文件上，风险在大文件上。★

**这条不解决就不要开工**——它决定 D2 是「几行」还是「一天」。

## 测试计划

单测（纯函数，够得着）：
- `promote_key(real_sha)` 的推导；「申报 ≠ 真值」时 `sha_verified` 的置位判定。

集成用例（★卡平台 O2 的测试 PG + 一个 S3★，已随消息 197 发给平台）：
1. complete 之后对象的真实 sha ≠ 申报 sha → **必须**记 `sha_declared_mismatch` 且 `sha_verified=false`，不是改库了事；
2. `blobs/<X>` 已被人引用时，第二个 begin **绝不能**落到同一个 key；
3. 直传 → 归位后 `s3_key` 必须是 `blobs/<真实哈希>`，且临时对象已删；
4. 两个人先后传同一份文件 → 第二个人零拷贝命中，且**内容确实相同**（读出来比对）。

机械门禁（不依赖测试 PG，现在就能加）：
- `scripts/blobkey-check.sh`：★除 `items.rs::blob_key` 之外，任何地方不得出现字面量 `"blobs/"`★。
  这条把 D1 的「谁能写规范 key」从一句设计说明变成可执行判据 —— 与 `ddl-check.sh` 同一个思路。
