## 1. 背景与目标

### 1.1 为什么做

congrove 目前是文档/材料存储（原「空间」+ 树 + 权限 + 分享；本文起统一称**项目**，见 D0）。它解决的是**会后**的问题——材料放哪、谁能看、怎么分享。

但真实的协作是一条链：**排会 → 开会 → 沉淀 → 复盘**。现在只有第三段有工具，前两段散落在微信群和口头约定里，第四段（复盘/统计）完全没有。结果是：

- 排会靠群里问「大家周三下午有空吗」，来回十几条消息才定下来
- 会议材料发在群里，翻聊天记录找；会后录屏没人传，或者传了没人知道在哪
- 到了季度总结，没人说得清「AI 组这季度开了多少次会、花了多少工时」

### 1.2 目标

一句话：**让一次会议从发起到归档只在一个地方发生，并且沉淀下来的东西天然可检索、可分享、可统计。**

拆成可验证的三条：

1. **排会不再靠猜**：发起人能看到参会人的忙闲（不是日程内容），冲突当场可见；参会人能一键提议改期。
2. **材料不再靠找**：会前材料、线上链接、会后录屏/纪要，都挂在同一个会议下；归档后自动落进对应项目，沿用现有的分享与权限。
3. **投入可度量**：按月/季/年，按项目，统计参会次数与时长；时长优先取录制的真实长度，而不是排程的名义长度。

### 1.3 非目标（本期明确不做）

写清楚不做什么，和写清楚做什么同样重要：

- ❌ **不自建音视频会议**。线上会议仍用腾讯会议/飞书/Zoom，我们只存**链接**。自建 SFU/MCU 是另一个量级的工程。
- ❌ **不做审批流、请假、报销、考勤**。「OA」这个词涵盖很广，本期只做**会议与日程**这一块。
- ❌ **不与外部日历双向同步**（Google/Outlook/飞书日历）。本期先做只出不进的 `.ics` 订阅（见 6.1.8），双向同步留待评估。
- ❌ **不做智能推荐会议时间**（自动找所有人都空的时段）。先把忙闲显示出来，让人自己选；自动寻优等有真实数据后再说。
- ❌ **不做会中实时协作**（实时笔记、举手、投票）。

| 删除与找回 | ✅ **已有** | 软删除 + 回收站 + 30 天保留 |

| **统计** | ❌ 没有 | 本期核心 |

**结论**：本期真正要新建的是**「会前 + 会中」的调度层**，以及**把它和已有的存储层接起来**。已有的转写/纪要能力直接成为需求 3 的答案——传上录屏，纪要自动就有了，不用人写。

## 3. 用户与角色

| 角色 | 是谁 | 关心什么 |
|---|---|---|
| **发起人**（Organizer） | 组织会议的人 | 快速定时间、通知到人、传材料、会后归档 |
| **参会人**（Attendee） | 被邀请的人 | 我什么时候有什么会、和我已有安排冲不冲、材料在哪 |
| **项目主持人**（owner，唯一） | 项目负责人 | 谁能进出项目、这个项目开了多少会花了多少时间 |
| **项目管理员**（admin，副手） | 主持人指定 | 增减成员、归档是否合规 |
| **项目成员** | 项目里的人 | 本项目全部资料（含我加入之前的） |
| **临时参会人**（D8） | 被邀请的非成员 | 只关心时间、议程和会议链接 |
| **旁听者**（D9） | 公开会议的路人 | 有什么公开的会可以去听 |
| **超管** | 平台管理员 | 全局统计、异常处理、强制转移 owner |

★**两类角色要分清**★:
- **项目角色**(主持人/管理员/成员)是**持久身份**,决定**能看什么资料**(D3)。
- **会议角色**(发起人/必参/选参/临时/旁听)是**相对某次会议**的,**不产生任何资料权限**。

## 4. 核心概念模型

先把名词定死，后面所有章节都用这套词：

```
项目（Project）★组织的基本单位,原「空间」★
 ├─ 可见性：公开(会议产生忙闲) / 私密(完全不占忙闲,可多人私下组队)
 ├─ 唯一主持人（owner）—— 只有他能指定/撤销管理员
 ├─ 若干管理员（admin,副手）—— 可增减成员
 ├─ 若干成员（member）—— 可读可传
 └─ 全部资料（一棵内容树）
      ★可见性规则:此刻是成员 ⟺ 看得到本项目全部资料(含加入之前的历史)★
      ★成员只能逐个加到人,没有「小组」这一层(D12)★

会议（Meeting）
 ├─ 单次会议：一个时间点
 ├─ 周期会议：一条重复规则（RRULE）+ 若干「例外」
 │    └─ 场次（Occurrence）：规则展开出来的**某一次**
 ├─ 关联 1..N 个项目 —— 一次会可同时讨论多个项目
 └─ 可见性 visibility：private（默认，仅被邀请者可见）/ public（全平台可见、可旁听，见 D9）

参与关系（Participation）
 └─ 某人 × 某次会议 → 角色（发起人/必参/选参/临时/**旁听**）+ 应答（待定/接受/拒绝/建议改期）
     ⚠ 参会**不产生任何资料权限**,权限只看项目成员身份(见 D3)

会议资料（Material）
 ├─ 会前:议程、待讨论文档、线上会议链接
 └─ 会后:录屏、录音、纪要、白板照片……
     └─ 底层就是 items;归属项目(决定权限与存储),会议只是一个**索引维度**
```

### 一句话说清三者关系

```
      材料的归属 = 项目          ← 唯一真相:决定权限、决定存不存得下
      材料的来源 = 某次会议       ← 只是索引:用来在时间线上找到它
      材料的位置 = 项目内的目录    ← 「2026-08-06 模型评审会」这样的文件夹
```

**同一份材料两条路径都能到达**（见 D7）：从项目树里翻到，或从时间线上某次会议点进去。
但**权限只算一次**——按项目成员身份，与走哪条路无关。

## 5. 关键设计决策

这一章是本文档最重要的部分——**十七个决策（D0~D16），每个都有真实的取舍**。设计和排期都依赖它们，请重点看。

### D0. 「空间」重构为「项目」★新增（v0.2）

**问题**：现有系统叫「空间」，而组织里真实存在的单位是「项目」。是维持两个概念（项目对应一个空间），还是合并？

**决策**：**合并——「项目」是唯一的组织单位，材料直接按项目组织**，不再有独立的「空间」概念。

理由：

1. **少一层抽象**。每次都要解释「项目对应一个空间」，这本身就是设计没对齐的信号。
2. **权限规则天然对齐**。R1「当前成员身份决定可见性」是**项目**的规则，不是「存储容器」的规则。挂在项目上，规则只有一句话。
3. **归档不再需要中间层**。会议直接关联项目，材料直接进项目——v0.1 里那套「会议 ↔ 空间挂钩」的中间概念整个删掉。

**现有机制的映射**（多数已具备，只缺一个 owner）：

| 新概念 | 现有机制 | 差距 |
|---|---|---|
| 项目 | `spaces` 表 | 更名 |
| 项目的全部资料 | 内容树（`items`） | 无 |
| **唯一主持人 owner** | 无 | ★新增字段 + 「只有 owner 能指定/撤销 admin」★ |
| 管理员（副手） | `admin` 角色 | 已有（可多个） |
| 成员 | `editor` / `viewer` | 已有 |
| 增减成员 | `space_grants` 增删 | 已有；★但要去掉按组授权，只留到人（D12）★ |

⚠ **这是破坏性重构**（表名、API、前端全涉及）。**现在是成本最低的时刻**——线上数据几乎为零；
晚做一个月，成本完全不同。详见 §10 风险。

**边界：不属于任何项目的材料放哪？**（个人草稿、跨项目模板、行政资料）
建议不做例外机制，而是**用项目本身承载**：建一个所有人都是成员的「公共资料」项目；
个人草稿放「个人项目」（只有自己一个成员）。规则保持唯一，不开特例。

### D1. 隐私与冲突：团队项目产生忙闲，个人项目完全隐形 ★★（v0.3 改写）

**问题**：要求「别人看不到自己的日历安排」，同时又要「有时间冲突时能看见并调整」。

**v0.2 的方案**：Free/Busy 模型 + 「个人可逐条标记某日程不占用忙闲」。
**v0.3 改为**：★**按项目的可见性开关自动分流**★，不用每次记得去勾。

| 项目可见性 | 它的会议/日程产生的忙闲 | 用途 |
|---|---|---|
| **公开** | **全平台可见**（只有忙/空，**无任何内容**） | 正常协作 |
| **私密** | ★**完全隐形**★——别人看到"空闲"，**发起人不知道我忙** | 私事、个人提醒、**几个人私下组队** |

#### ★命名修订（2026-08-06 原型评审）：不叫「团队/个人」，叫「公开/私密」★

原方案按 `kind = team | personal` 分。评审时发现它**把「人数」和「隐私」绑死了**：

> 「有时候几个人私下组队也不想公开，后续想公开了再改。」

这种情况在 team/personal 的二分法里**无法表达**——它不是个人的（有好几个人），
但也不该产生忙闲。改成 `visibility = public | private` 后与人数彻底解耦：

| 场景 | 可见性 | 成员数 |
|---|---|---|
| 正常项目组 | 公开 | 多人 |
| **私下组队** | **私密** | **多人** ← 原方案表达不了 |
| 我的日程 | 私密 | 1 人（自动创建） |

而且**随时可改**——私下攒的局成熟了，一个开关就转公开。

#### ⚠ 「公开」这个词有歧义，UI 必须消歧

之前已定：公开项目**只有忙闲可见，项目名称与成员名单都不公开，资料更不公开**。
但标签只写「公开项目」，人会以为**资料也公开了**——这个误解的代价是
有人不敢用，或者更糟：**有人以为设成私密了、其实没有**。

**因此这个开关旁必须有一处消歧说明**（原型里做成 ⓘ 悬停）：

> 只影响忙闲：公开项目的会议会让成员在别人眼里显示「忙」（仅忙/空，不含标题）。
> 私密项目的会议完全不占忙闲，别人看到的是空闲。
> **两者的资料都只有成员能看，项目名称与成员名单也都不公开。随时可以改。**

这不是可省的注释——它是隐私开关的必要文案。

```
发起人看到的:
  张三  09:00 ██████ 11:00     ← 团队项目的会,显示忙(但不知在干嘛)
  李四            10:00 ████   ← 同上
  王五  （全天空闲）            ← ★可能真空,也可能有私事——发起人无从分辨★
```

**这不是漏洞，是刻意的**：私事连"我忙"这件事都不该暴露。代价是发起人可能排到王五头上，
于是：

#### 三条随之而来的硬要求

1. ★**系统必须醒目提醒当事人**★：王五收到邀请时，界面要直接标红
   「此时段你有个人安排」，并把「建议改期」按钮放在旁边。
   **发起人看不见，就只能靠他自己发现——不提醒就一定会漏。**
2. **「建议改期」不是便利功能，是私事冲突唯一的出口**（见 D2）。
3. **会议讨论区的私聊**是第二条出口——有些事需要说明原因而不只是换个时间（见 D13）。

#### 其它约定

- 「团队项目全平台可见」**仅指忙闲**；**项目名称与成员名单都不公开**
- 每人**自动获得一个「我的日程」个人项目**，也允许再建多个
- 个人项目**能存材料**，完全私密（兼作个人网盘）
- **模型简化**：个人日程 = 个人项目里的会议 → `personal_events` 表**删除**

### D2. 冲突不阻塞，走「建议改期」协商 ★

**问题**：冲突了怎么办？系统硬拦，还是允许？

**决策**：**冲突永远只是警告，不是阻塞**。理由：系统不知道优先级——张三那个"忙"可能是可以推掉的自习。

协商用 iCalendar 标准的四个动作（RFC 5546 iTIP）：

| 动作 | 谁做 | 效果 |
|---|---|---|
| **接受 / 拒绝 / 待定** | 参会人 | 更新应答状态，发起人可见 |
| **建议改期**（COUNTER） | 参会人 | 附上建议的新时间 + 理由，推给发起人 |
| **采纳 / 驳回改期** | 发起人 | 采纳则会议时间变更并通知全员重新应答 |

这正好对应你说的「冲突的话可以由参会人进行调整，或者回复让发起人调整时间」——**两条路都有**：小事自己调（改自己那个冲突的日程），大事请发起人调（建议改期）。

### D3. 权限的唯一来源是「当前项目成员身份」★★★（v0.2 整条重写）

> **v0.1 的方案已被推翻，此处记录原因——它是这份文档里最有价值的一次纠错。**

#### 你的规则，形式化

| # | 规则 |
|---|---|
| **R1** | 可见性由**当前项目成员身份**决定 —— 加入即可见**全部历史**，离开即失去**全部**（含他本人参与过的会议） |
| **R2** | 每个项目**恰好一个**主持人 |
| **R3** | 主持人可指定若干**管理员**（副手） |
| **R4** | 主持人/管理员可随时增减成员 |
| **R5** | 一个人可属于多个项目 |
| **R6** | 一次会议可讨论多个项目，内容分别落到各项目 |

**R1 有个很干净的性质**：权限是「**当前状态的函数**」，不是「历史事件的累积」。

```
能看到 X  ⟺  此刻是 X 所属项目的成员
（与"当时在不在项目里"、"参没参加过那次会"完全无关）
```

这比按历史授权简单得多，也更好审计——任何时刻只要查一张成员表就知道谁能看什么，
不必回溯谁在哪年参加过哪次会。

#### 为什么 v0.1 的方案错了

v0.1 设计的是「**参会 → 获得该会议材料的子树授权**」。放到 R1 下，它**两头都违反**：

| 场景 | v0.1 的行为 | R1 要求 |
|---|---|---|
| 张三 3 月参会 → 6 月被移出项目 | **仍持有 3 月那次的授权，照样能看** ✗ | 离开即全失，含他参与过的 |
| 李四 9 月加入项目（没参加过 3 月的会） | **拿不到授权，看不到历史** ✗ | 加入即可见全部历史 |

根因：v0.1 把权限建成了**历史事件的累积**（参加过就永久拥有），而你要的是**当前状态的函数**。

#### 现在的决策

**权限唯一来源 = 当前项目成员身份。参会不产生任何持久权限。**

```
effective(用户 U, 材料 I) =
    U 在 I 所属项目上的角色（owner / admin / member）
    若 U 不是该项目成员 → 无任何权限（404）
超管全局覆盖。
```

**这反而让实现更简单**——v0.1 要新建的 `item_grants` 子树授权表**不需要了**，
现有的项目级授权（`space_grants` → `project_members`）就够用。少一张表、少一处权限推导分支。

#### 三条随之而来的硬要求

1. ★**移出成员时，必须连带撤销他创建的、指向该项目内容的所有公开分享链接**★
   否则 R1 名存实亡：张三离开前生成一条公开链接，离开后那条链接**照样能打开**，等于留了个后门。
   （现有公开分享是**绕过项目成员身份**的独立通道，这条不写进需求就一定会漏。）
2. **移出成员后，该项目的会议从他的时间线上消失**（见 D7）。
3. **加入成员时不需要任何回填动作**——因为权限是当前状态的函数，加进去自然就能看全部。
   ⚠ 反过来说：**任何"授权生效时间"的字段都不要加**，那会把模型退回历史累积。

### D4. 一次会议多个项目：整份进所有关联项目 ★已拍板

**问题**：8 月 6 日的会前 30 分钟讨论项目 A、后 30 分钟讨论项目 B，整场录屏怎么归档？

**决策（你已拍板）**：**整份进所有关联项目**，不做按议题切分。

技术形态：**每个项目各建一行 item，指向同一个 `blobs/<sha256>` 对象**。

- **存储零成本**：内容寻址保证同内容全库一份（现成能力）
- **权限天然隔离**：两个项目各管各的，A 设了禁下载不影响 B
- **删除安全**：现有引用计数（含软删除行）保证删一边不影响另一边

**已知并接受的代价**：只参与 A 的人会听到录屏里 B 的讨论。你的判断是大家不介意互相听到，
**因此这不是缺陷而是明确的取舍**。若将来要隔离，可升级为「上传时勾选给哪几个项目」
（零技术成本、靠人把关），而不必去做录屏切片转码（开销大、议题边界要人工确认）。

**否决的备选**：跨项目软链（一行 item 指向另一个项目的内容）。看着优雅，但会造成
**跨项目的权限旁路**——正是本仓库刚做过的安全审计一直在防的那类洞（2026-08-06 补的 11 处
`deleted_at` 过滤就是同类问题）。不值得为省几行数据库记录引入一个权限旁路。

### D5. 时长口径：三级回退 + 记录来源

**问题**：你说「时长根据录音、录屏计算，没有的根据用户录入」。但如果排程 1 小时、录屏 2 小时，算几小时？

**决策**：**优先级回退，并且把「这个数字怎么来的」一起存下来**：

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1（最高） | **录制时长** | 录屏/录音的真实时长（现有转写流程已经能拿到） |

#### ★「录制」与「材料」必须是两个入口★（2026-08-06 原型评审补充）

**问题**：会议材料里本来就可能有视频（会上放的演示片、实验录像）。
如果和「这场会的录屏」混在一起，**时长会算错、GPU 会白烧**。

| | 录制 | 材料 |
|---|---|---|
| 是什么 | **这场会议本身**的录像/录音 | 议程附件、参考文档、**会上放的演示视频** |
| 会被转写吗 | ✅（只对最长的一份） | ❌ |
| 计入会议时长吗 | ✅ **时长口径的依据** | ❌ |
| 入口 | 会议详情页 →「**录制**」 | 会议详情页 →「材料」 |

**实现要点**：`items` 需要一个标记区分二者（如 `is_recording`）。
★判据是「上传到哪个入口」，不是「是不是视频文件」★——同一个 mp4，
传进「录制」就是这场会的记录，传进「材料」就是会上讨论的素材。

⚠ 若不做这个区分，D5 的「优先取录制时长」就没有可执行的判据——
系统无法分辨 1.8GB 的录屏和 200MB 的演示视频哪个才代表会议长度。
| 2 | **手工录入** | 发起人会后填写的实际时长 |
| 3（兜底） | **排程时长** | 结束时间 − 开始时间 |

统计界面**必须显示口径来源**（如「本季度 42.5 小时，其中 31 小时来自录制、8 小时手工、3.5 小时按排程估算」）。理由：这个数字会被用来做汇报，来源不透明就会有争议；标出来源，争议时可追溯。

多个录制文件时取**最长的那个**，不累加（两个人各录一份是同一场会，累加会翻倍）。

### D6. 统计去重：分组展开、总计去重

你的原话已经很明确，这里只是固化成规则：

```
分组统计:  按 (会议 × 项目) 展开 —— 一个会挂两个项目,两个项目各算一次
总计统计:  按 会议 去重      —— 同一个会在季度/年度总数里只算一次
```

SQL 上就是 `COUNT(*)` 与 `COUNT(DISTINCT meeting_id)` 的区别。**时长同理**：分组各算各的，总计按会议去重后只加一次。

> ⚠ 统计本身会泄露日程信息（见 11.2）——「张三本季度开了 50 小时会」暴露了他的活动量。需要你定可见范围。

### D7. 材料的两个入口：项目视图 与 时间线视图 ★新增（v0.2）

**问题**：同一份录屏，用户可能从两个方向去找它——「AI 项目里那份评审录屏」或「上周三那个会的录屏」。

**决策**：**两个入口，一个真相**。

```
       存储与权限的唯一真相：材料属于哪个项目
                    │
        ┌───────────┴───────────┐
   【项目入口】              【时间线入口】
   按项目浏览全部资料          按时间看我的会议
   （我是成员就看得全）        每次会议下挂它的材料
        │                       │
        └───────→ 同一批 items ←─┘
```

| | 项目入口 | 时间线入口 |
|---|---|---|
| 组织方式 | 目录树（含「日期 会议名」文件夹） | 按时间倒序的会议流 |
| 回答的问题 | 「这个项目有哪些资料」 | 「我上周开的那个会，材料在哪」 |
| 范围 | 我参与的每个项目的**全部**资料 | **我参与过的会议**（且我此刻仍有权看） |
| 权限判定 | 项目成员身份 | **同上**——入口不同，判定同一套 |

**关键约束**：时间线只是**索引**，不是第二套权限。

- 我被移出项目 A → A 的会议**从我的时间线上消失**（不是显示但打不开——那等于告诉我「这个项目还在开会」）
- 材料的 URL 只有一个（它在项目里的位置），时间线只是**指过去**，不复制、不另建一套地址

对应你的需求 4「个人在自己的面板可以根据时间线看自己的安排」——时间线入口同时承担
**未来（我接下来有什么会）** 与 **过去（我开过的会及其材料）** 两段。

### D9. 公开会议与旁听 ★新增（v0.2）

**需求**：有些会议对全平台公开（**由主持人决定**）。公开后，非项目成员也能看到「哪个项目在开会」、
可以**旁听**，但**只能拿到地点（线下地点 / 线上会议链接），拿不到任何会议资料**。

#### 关键洞察：这是两个正交的维度

这条需求**完全不需要改 D3**。因为它动的是「会议元信息给谁看」，而 D3 管的是「资料给谁看」——
两者互不相干：

```
维度一:资料可见性  ← 唯一由「当前项目成员身份」决定(D3,不因公开而放宽)
    成员 → 全部可见
    非成员 → 一律 404

维度二:会议元信息可见性  ← 由会议自己的 visibility 决定(本决策)
    private(默认) → 仅被邀请的人知道这个会存在
    public        → 全平台可见,任何人可旁听
```

两个维度独立组合，四种情况都成立且合乎直觉：

| | 资料 | 会议元信息 |
|---|---|---|
| 项目成员 | ✅ 全部 | ✅ 全部 |
| 被邀请的临时参会人（D8） | ❌ | ✅ 时间/标题/议程/链接 |
| **公开会议的旁听者**（本决策） | ❌ | ✅ 时间/标题/**议题与议程**/**地点与链接**/所属项目 |
| 无关的人 + 私密会议 | ❌ | ❌ 连"存在"都不知道 |

**这个正交性是设计健康的信号**：新增一整类用户，权限模型一行没改。

#### 决策

- 会议增加 `visibility` 字段：`private`（默认）/ `public`，**只有项目主持人或会议发起人能改**
- 公开会议进入**「公开会议」列表**（新入口，见 6.1.8），全平台可浏览
- 旁听者可**主动标记「我要旁听」** → 该会议进入他的个人日历
- 旁听者**能**看到：所属项目名、会议标题、**议题与大致议程**、时间、**线下地点、线上会议链接**
- 旁听者**看不到**：任何会前/会后材料、纪要、录屏——与 D3 完全一致，不开特例

#### ★「议程」与「会前材料」必须是两样东西★

这条需求逼出一个重要的设计边界。旁听者要能看议程、但不能看材料，所以两者不能混在一起：

| | 是什么 | 存在哪 | 谁能看 |
|---|---|---|---|
| **议题 / 议程** | 会议自带的一段**文本字段**（几行要点） | `meetings.agenda` 列 | 公开会议 → **所有人** |
| **会前材料** | 上传的**文件**（待讨论的论文、数据、PPT） | `items`（项目内） | **仅项目成员** |

**设计含义**：会议详情页必须内置一个「议程」文本框，而**不是**让人传一个 `议程.docx`。
否则边界就糊了——传成文件的议程属于材料，旁听者看不到，与你的要求相悖。

UI 上要把这件事说清楚：议程框旁注明「**此处内容对公开会议的旁听者可见**」，
避免有人把敏感细节写进议程。

#### 三个边界（★已拍板★）

1. **不暴露参会人名单**——只显示**发起人 + 参会人数**。名单等于项目成员构成，不该全平台可见。
2. **旁听不计入统计**。旁听者的出席由**主持人会后补录姓名**、记进会议纪要（见 D11）。
3. **标记旁听后占用忙闲**——我打算去听，那个时段确实不空，别人约我时应该看到冲突。

### D13. 会议讨论区：公开讨论 + 私聊 ★新增（v0.3）

**问题**：D1 让个人项目的日程完全隐形——发起人**不知道我忙**。那我怎么跟他说？

**决策**：会议详情页内置讨论区，**两个频道**：

| 频道 | 谁能看 | 谁能发 | 通知 |
|---|---|---|---|
| **公开讨论** | 参会人（含临时参会人） | 同左（**旁听者不能发**） | 只标未读，**不发站内信** |
| **私聊** | 仅双方 | 可私聊**发起人 + 项目主持人** | ★**必发站内信**★ |

**为什么私聊必通知、公开讨论不通知**：私聊是点名找你（改期协商往往是急事，几小时内要定）；
公开讨论每条都推会把站内信洗版。

#### ★边界：私聊只限这两个角色，绝不做任意点对点★

一旦允许「私聊任何参会人」，这就是一个完整的 IM，会持续吸走维护精力，
而平台可能已有更合适的工具做这件事。**这条边界要在实现时守住。**

- 旁听者**不能发言**——公开会议可能来很多人，防刷屏
- 聊天记录**保留在会议详情页，不进材料**（不占项目目录，权限跟会议走）

### D14. 纪要由「会议记录员」按固定模板整理，AI 只是原材料 ★★★新增（v0.3）

> **这条纠正了我对纪要功能的根本误解**，是本轮走查最有价值的一次修正。

| 字段设计 | ★**通用到能覆盖各类会议**★——只有一种模板，用不上的留空，**不为某类会议特化** |
| 参会/旁听名单 | 系统带出邀请名单，**记录员核对修改**（这就是"补录实际到场"，D11） |
| 待办事项 | ★**先当普通文本写**，不做结构化任务系统★（一旦做成任务就要跟踪、提醒、统计完成率，是另一个产品） |
| 状态 | **草稿 / 已完成** 两态；完成后通知全员 |
| 编辑权 | **所有参会人都能编辑**（现有版本历史 + 一键恢复作兜底） |
| 多份录制 | 材料**都保留**，★**只对最长的那份生成参考稿**★（避免重复耗 GPU、避免出两份纪要） |
| 催办 | 会后若干天仍是草稿 → **给记录员发提醒** |

### D15. 纪要 PDF 走 LaTeX，并提议平台起共享编译服务 ★新增（v0.3）

**决策**：记录员写 **Markdown** → 系统**转 LaTeX 套模板** → 出 **PDF**。

| # | 决策 |
|---|---|
| 生成时机 | **点「完成」时生成并存档**；之后修改可**重新生成新版本**（进版本历史） |
| 为什么存档 | ★内容冻结★——事后改纪要不会悄悄改变已经发出去的那份 PDF |
| 渲染失败 | ★**报错并附日志片段，绝不静默**★——要能告诉记录员第几行有问题 |

#### ★平台已立项：共享 LaTeX 编译服务★（提议 #118 → 平台确认 #119，2026-08-06）

| 各子系统自装 | 平台共享服务 |
|---|---|
| 每镜像 +800MB~1.5GB，N 家 ×N 份 | 一份 |
| 构建要走镜像源装 TeX（congrove 曾因 900s 死线挂过构建两次） | 子系统镜像回到几十 MB |
| 推大层进内网 registry 会和 Garage 大宗写抢带宽（记录在案的坑） | 不涉及 |
| 字体/宏包版本各不相同 → PDF 观感不统一 | 全平台统一 |

★**必须在第一版就锁死的安全边界**★：LaTeX **图灵完备、能读写文件、能执行 shell**
（`\write18{...}` 执行任意命令、`\input{/etc/passwd}` 读任意文件）——
**「提交源码就编译」本质上是一个远程代码执行接口**。要求：

1. **禁 shell escape**（`-no-shell-escape`，不用 restricted）
2. **限文件读写**：`openin_any=p` / `openout_any=p`
3. ★**无网络**★（NetworkPolicy 全禁 egress——能联网就能外带数据）
4. **wall-clock 超时**（LaTeX 可以写死循环）+ 内存/CPU limit
5. **只读根文件系统** + 每次编译一个临时空目录，编完即删
6. **输入输出限大小**

**平台的答复（#119）**：★**已立项开工**★。我列的 6 条安全边界**全部采纳**，并加了纵深：
容器沙箱（非 root + drop all caps + seccomp + 只读 rootfs + tmpfs 空目录编完即删）、
NetworkPolicy 全禁 egress、**并发闸**（xelatex 是 CPU 密集的，多家同时批量出 PDF 会打满节点
——这条是平台补的，我漏了）、鉴权复用平台 key 体系。接口即我建议的无状态
`POST /compile`（multipart: main.tex + 图片/cls）→ PDF 或**带行号的日志片段**，默认 xelatex，
跑 CPU 节点不占 GPU。落地后平台会在群里同步调用地址与字体清单。

**congrove 侧的影响**：★**镜像不用动**★，只提交 tex。M4 的 PDF 不再需要预留"多一轮装 TeX"的排期。

**我追加的建议（#120，待平台答复）**：**服务除 .tex 外也接受 Markdown 输入**。
理由是大多数子系统手里的内容是 md 而非 tex（congrove 的纪要就是记录员写 md），
若只吃 tex 则每家都要自己做一遍 md→tex：装 pandoc 是重复依赖、**转换质量不一致**导致
PDF 观感仍不统一，而且**转义没做好就是注入面**（用户在 md 里写 `\write18`，
某家转换器直接透传的话，沙箱就成了最后一道防线）——**统一在服务侧转义更安全**。
建议 `/compile`（收 tex）与 `/compile-md`（收 md + 模板，服务侧统一转义）两个入口并存；
若第一版不做 md 入口，至少把**安全的转义规则写进文档**，别让每家自己发明一套。

### D16. 搜索：先覆盖纪要与会议 ★新增（v0.3）

**问题**：v0.2 把搜索列为「暂不做」。但有了 D14 的结构化纪要之后，
「三个月前那个会到底定了什么」成为**主线需求**，翻目录已经不够。

**决策**：**做搜索，先只搜纪要与会议**（标题、议程、纪要正文、参会人）。

- **不做**材料全文抽取（PDF/Word 内文）——工作量大一级，且纪要已覆盖大部分检索意图
- 纪要是结构化文本、量不大，**PG 全文检索足够**，不需要引入新组件
- ★权限过滤必须在查询层★：只能搜到**我此刻还是成员的项目**里的东西（D3）

### D10. 材料的组织：会议区（只读）+ 自由区 ★新增（v0.2）

**问题（你提出）**：会议材料按**时间**组织（一次会 = 一个「日期+主题」文件夹），
但项目里还有**不属于任何会议的日常资料**；主持人后期还可能要把多次会议的材料重新分门别类。

**你的决策**：★**会议区在项目树里是只读的**★——材料只能从**会议详情页**进出，
项目树里那份是它的**只读投影**。要改动就回会议详情页改。

> 理由（你的原话）：「这样功能独立，大家使用的时候也不用解释。」
> ——两处都能上传的方案要向用户解释「为什么在这个文件夹传会自动挂到那个会上」，
> 而**单一入口不需要任何解释**。

#### 项目内的两个区

```
项目「AI 模型」
├── 会议/                        ← ★会议区:只读投影★
│   ├── 2026-08-06 模型评审会/    ← 系统自动建,带 meeting_id
│   │   ├── 议程附件.pdf          ← 只能看/下载/复制/分享
│   │   ├── 录屏.mp4             ← 要增删改 → 去会议详情页
│   │   └── 纪要.md
│   └── 2026-07-20 周会/
│
├── 论文/第三版/                  ← ★自由区:完全自由★
│   └── 录屏.mp4  ←── 从会议区**复制**来的副本,独立归自由区管
│
└── 日常资料/                     ← 与任何会议无关
    └── 参考文献.pdf
```

#### 会议区允许什么、禁止什么

| 操作 | 会议区 | 说明 |
|---|---|---|
| 查看 / 播放 / 预览 | ✅ | 按项目成员身份判权（D3） |
| 下载 | ✅ | 受会议的禁下载开关约束（6.3.2） |
| **复制到自由区** | ✅ | ★零存储成本（内容寻址）★ |
| **生成公开分享链接** | ✅ | 受会议的禁分享开关约束 |
| 上传 / 新建 | ❌ | → 去会议详情页 |
| 重命名 / 移动 / 删除 | ❌ | → 去会议详情页 |

**唯一的写入口是会议详情页。** 项目树那边给出「在会议详情页中管理 →」的跳转。

#### 这个约束意外地更好——会议记录变得不可篡改

原方案允许把材料从会议文件夹搬走，会造成一个尴尬：**会议记录会被人搬空**。
改成只读之后：

- **会议区 = 完整、稳定的会议记录**（有审计价值：这次会当时产出了什么，一直在那）
- **自由区 = 整理的成果**（爱怎么折腾怎么折腾）

你最初的诉求「主持人把不同次会议的材料分门别类存放」，现在的答案是
★**复制到自由区去整理，原件留在会议里不动**★——两个目的同时达成，且互不干扰。

#### 副本是独立的

**从会议区复制到自由区的那一份，不再关联任何会议。**

- 它是自由区的普通材料，归项目管，可随意改名/移动/删除
- 删掉副本**不影响**会议区的原件；从会议详情页删掉原件**也不影响**副本
- 底层仍共享同一个 `blobs/<sha256>` 对象，**不多占一个字节**

这正是「功能独立」——两边各管各的，不需要向任何人解释联动规则。

#### 会议删除时

- 会议被删 → 它的会议区文件夹一并进回收站（可还原）
- **已复制到自由区的副本不受影响**（它早就独立了）

#### 数据模型影响

`items.meeting_id` 只用来**标记「这是某会议的只读区」**，用于展示与跳转，
**不再需要「在此文件夹下上传自动继承 meeting_id」那套继承逻辑**——因为根本不允许在这里上传。
少一条隐式规则。

### D11. 「实际到场」是会后补录的事实 ★新增（v0.2）

**问题**：统计该按「接受了邀请」算，还是按「真的来了」算？线上会议我们**拿不到实际到场数据**。

**决策（据你所述）**：区分两件事——

| | 是什么 | 何时产生 | 用途 |
|---|---|---|---|
| **邀请应答** | 会前的**意向**（接受/拒绝/待定） | 会前 | 发起人判断能不能开 |
| **实际到场** | 会后的**事实**（谁真的来了） | 会后由**主持人补录** | 统计、纪要 |

- 主持人可在会后**补录实际到场人员**，包括**旁听者的姓名**（旁听者不在邀请名单里）
- 这份名单**写进会议纪要**
- **统计口径**：有补录 → 以补录为准；没补录 → 退回「接受邀请且会议未取消」

这条同时**回答了 11.5 的统计口径问题**，该条可关闭。

### D12. 删除「小组」概念，权限精确到人 ★新增（v0.2）

**问题（你提出）**：现有系统有「组」（`groups` / `group_members`），可以按组给项目授权。
但你要求**每个项目必须确认到具体的人**，不通过小组间接确定权限。

**决策**：**删除「组」这个持久概念，项目成员只能逐个添加到人。**

**为什么这是对的**（与 D3 同一个方向）：

1. **权限来源唯一**。现有推导是 `max(直接授权, 所属各组的授权)`——两个来源意味着
   「张三为什么能看到这个」需要推导。删掉组之后，答案永远是一句话：**他在成员名单里**。
2. **移除立刻确定**。现在把人从项目里删掉，他可能**还从某个组继承着权限**，
   而这正是 R1「离开即失去全部」最容易失守的地方。
3. **名单可核对**。主持人打开成员列表看到的就是**确切的人名单**，不是「A 组 + B 组 + 张三」这种需要展开才知道是谁的表达。

**代价与对策**：每年新人加入要逐个添加。用**批量操作的 UI** 解决，而不是靠「组」这个持久概念：

- 成员管理页支持**多选用户一次性加入**
- 邀请参会人时支持**「导入某项目的全部成员」**——这只是一个**选人快捷方式**，
  导入后落成的仍是一个个具体的人，**不建立任何持久的组关系**

★**项目成员列表本身就是天然的「组」**★——不需要在它之外再造一个 `groups` 概念。

**实现影响**：`perm.rs` 的有效权限推导从

```
effective(U,S) = max(U 在 S 的直接授权, U 所属每个组在 S 的授权)
```
简化为
```
effective(U,P) = U 在项目 P 上的角色（不在名单里 → 无权限）
```

少一次 JOIN、少一处分支。`groups` / `group_members` 两张表随 D0 的重构一并删除。

### 6.1 日历与日程（对应需求 1）

#### 6.1.1 个人日历视图 · P0

**用户故事**：作为参会人，我想在一个视图里看到我所有的会和日程，这样我不用在群里翻消息。

- 支持**日 / 周 / 月 / 列表**四种视图，默认周视图
- 显示：会议标题、时间、发起人、我的应答状态、所属分组（颜色区分）
- 待应答的邀请**置顶高亮**
- 可建**纯个人日程**（不邀请任何人，仅自己可见，可选是否占用忙闲）

**验收标准**：
- [ ] 新建一个会议后，所有参会人的日历在**刷新后**能看到它（不要求实时推送）
- [ ] 其他人看我的日历，只能看到忙闲块，看不到标题和任何详情
- [ ] 标为「不占用忙闲」的个人日程，别人查我忙闲时**完全不出现**
- [ ] 跨天、跨月边界的会议在各视图里显示正确

#### 6.1.2 发起会议 · P0

**用户故事**：作为发起人，我想选好时间和人就把会发出去。

必填：标题、开始时间、结束时间、参与人
选填：**关联项目**（1..N）、线下地点 / 线上链接、**议题与议程**、是否周期性、**是否公开**（D9）

- 参与人分**必参 / 选参**（选参的冲突不计入「有冲突」的红色提示）
- 选人时支持**逐个选用户**，或**「导入某项目的全部成员」**作为快捷方式
  （★只是选人快捷方式，不建立任何持久的组关系，见 D12★）
- 保存后自动给每位参会人发**站内信**（复用现有能力）

**验收标准**：
- [ ] 结束时间早于开始时间 → 拒绝并提示
- [ ] 参与人为空 → 允许（等于个人日程）
- [ ] 邀请了不存在的用户名 → 走现有 `users/exists` 校验，明确报错
- [ ] 时长超过 24 小时 → 警告但允许（跨天集训确实存在）

#### 6.1.3 忙闲与冲突提示 · P0

**用户故事**：作为发起人，我想在定时间时就看到谁撞了，而不是发出去才被告知。

- 选完人后，时间选择器上**并排显示每个人的忙闲条**
- 拟定时段与任何**必参人**的忙闲重叠 → 红色提示「N 人时间冲突」，可展开看是谁
- **冲突不阻止发送**（见 D2）

**验收标准**：
- [ ] 忙闲只返回时间区间，响应体里**不含**任何标题/内容字段（按接口契约校验，防止将来有人顺手加字段）
- [ ] 忙闲查询覆盖：单次会议、周期会议展开的场次、个人日程
- [ ] 参会人 20 人时，忙闲查询在 1 秒内返回

#### 6.1.4 应答与协商 · P0

**用户故事**：作为参会人，我时间冲突了，想让发起人换个时间。

四个动作：**接受 / 拒绝 / 待定 / 建议改期**

- 「建议改期」需填：建议的新时间段（必填）+ 理由（选填）
- 发起人收到后可**采纳**（会议改期，全员状态重置为待应答并再次通知）或**驳回**（附理由）
- 所有应答变化都进审计（复用现有 `audit`）

**验收标准**：
- [ ] 发起人采纳改期后，全员应答状态重置为「待定」，并各收到一条站内信
- [ ] 参会人可以反复修改自己的应答（接受后又拒绝是允许的）
- [ ] 会议开始后不再允许「建议改期」（但仍可标记拒绝/未参加）

#### 6.1.5 周期性会议 · P0

**用户故事**：作为发起人，我想设「每周三下午 3 点的组会」，一次设好。

- 支持规则：每天 / 每周（可多选星期几）/ 每月（按日期或按「第 N 个星期几」）/ 自定义间隔
- 结束条件：永不 / 重复 N 次 / 到某日期为止
- ★**单场次可独立修改**★：改这一场的时间、换链接、取消这一场，**不影响整个系列**
- 修改时明确询问「仅此一场 / 此后所有场次 / 整个系列」

**技术约束（写进需求是因为它会影响用户可见行为）**：
- 采用 **iCalendar RFC 5545 的 RRULE** 表达规则，**存主记录 + 例外记录**，不预先展开成 N 行
- ⚠ **时区必须存 IANA 名称**（`Asia/Shanghai`），不能存固定偏移。虽然中国无夏令时，但一旦有跨时区参会人，按偏移存的规则会在对方那边整体漂一小时

**验收标准**：
- [ ] 「每周三 15:00」跨越月末、年末仍正确展开
- [ ] 取消其中一场，其余场次不受影响，且该场次不再出现在任何人日历与忙闲里
- [ ] 修改「此后所有场次」后，历史场次保持原样（不追溯篡改已发生的会议）
- [ ] 周期会议展开的场次参与忙闲计算（不能因为是"虚拟"的就漏掉）

#### 6.1.6 会议分组 · P1

**用户故事**：作为参会人，我想知道这是 AI 组的会还是产品组的会。

- 会议归类**直接用关联项目**（不再另造「分组」概念）；一个会挂多个项目就同时属于多个分组
- 日历上用颜色区分
- 统计按分组切分（见 6.5）

#### 6.1.7 公开会议广场 · P1（D9）

**用户故事**：作为平台上任何一个人，我想知道最近有哪些公开的会可以去听。

- 独立入口，**全平台可见**，列出所有 `visibility=public` 的会议
- 每条显示：所属项目、会议标题、**议题与大致议程**、时间、**线下地点 / 线上链接**、发起人

- [ ] 只有项目主持人或会议发起人能切换公开/私密

#### 6.1.8 日历订阅（.ics 只读） · P2

导出个人日历为 `.ics` 订阅地址，可加进手机系统日历。**只出不进**，避免双向同步的一致性泥潭。订阅地址需可撤销（复用公开分享的令牌思路）。

---

### 6.2 会议详情与会前材料（对应需求 2）

#### 6.2.1 会议详情页 · P0

一次会议一个页面，包含：

- 基本信息（时间、发起人、**关联项目**、议题与议程、是否公开）
- **参会人列表与应答状态**（谁接受了、谁没回、谁建议改期）
- **线上会议链接**（★可随时更改，改动通知全员★）
- **会前材料**（议程、待讨论文档等）
- 会后区域（录屏、纪要，见 6.3）

**验收标准**：
- [ ] 发起人改了线上链接 → 全员收到站内信，日历上的会议也显示新链接
- [ ] 链接变更有历史记录（谁在什么时候改的，改成什么）——开会前十分钟被改链接是真实场景，要能追溯
- [ ] 非参会人访问会议详情 → **404**（不是 403，不暴露"这个会存在"）

#### 6.2.2 会前材料上传 · P0

- **参会人均可上传**（不限发起人）
- 复用现有上传能力（大文件直传、秒传、断点续传全部自动继承）
- 材料按 D3 落在会议归档文件夹里，参会人对该子树有 editor 权限

### 6.3 会后归档（对应需求 3）

#### 6.3.1 会后材料上传 · P0

**用户故事**：作为参会人，我录了屏，想传上去让大家都能看。

- **任何参会人都能传**录屏 / 录音 / 纪要 / 其它材料
- **所有参会人都能看**
- ★传上音视频后**自动**转写并生成纪要★（现有能力，直接继承——这是需求 3「会议纪要」的答案，不需要人手写）

**验收标准**：
- [ ] 参会人 A 传的录屏，参会人 B 能看能播
- [ ] 传完音视频后自动排队转写，纪要生成后通知参会人
- [ ] 非参会人拿到直链也打不开（404）

#### 6.3.2 会议材料权限 · P0

**用户故事**：作为发起人，这次会涉及敏感内容，我想让大家能看但不能下载。

- 发起人 / 项目主持人 / 项目管理员 / 超管可对**该会议的材料**设置：
  - 是否允许下载原件（沿用现有 `viewer_no_download` 的语义，但作用在会议粒度）
  - 是否允许对外分享（生成公开链接）
- 默认：可看、可下载、可分享

**验收标准**：
- [ ] 设为禁下载后，参会人仍可在线播放/预览，但 `/download` 被拒
- [ ] 设为禁分享后，「分享」入口对非管理员隐藏**且后端拒绝**（前端隐藏不是安全边界）

### 6.4 归档到空间（对应需求 5）

#### 6.4.1 自动归档 · P0

**用户故事**：作为组员，我想会议材料自动进到组的空间里，不用手动搬。

- 会议可关联 **1..N 个空间**
- 归档目标路径：`<空间根>/<会议分组或"会议">/<YYYY-MM-DD 会议名称>/`
- 会议材料自动出现在每个关联空间（按 D4：各建行、共享对象）
- 进入空间后，**沿用空间自身的权限与分享能力**——需求 5 说的「这样可以分享」自动成立

**验收标准**：
- [ ] 关联两个空间时，两边都能看到材料，且**存储只占一份**（可通过对象引用计数验证）
- [ ] 在 A 空间删除归档材料，不影响 B 空间（引用计数保证对象不被误删）
- [ ] 会议名称含 `/`、空格、emoji 时，文件夹名不出错
- [ ] 同一天同名会议归档两次 → 不覆盖，追加序号

#### 6.4.2 归档时机 · P1

三选一（见 12.4，待你定）：会议结束后自动 / 发起人手动点「归档」/ 上传即归档。

### 6.5 统计（对应需求 6）

#### 6.5.1 个人统计 · P0

**用户故事**：作为参会人，我想知道我这个季度花了多少时间在会上。

- 维度：**月 / 季 / 年**
- 指标：参会**次数**、参会**时长**、按**分组**拆分
- 明确显示**时长口径来源**（见 D5）

#### 6.5.2 分组统计 · P0

**用户故事**：作为组负责人，我想知道 AI 组这季度开了多少会。

- 按分组/空间：会议次数、总时长、人均时长、参会率（接受人数 / 邀请人数）
- ★去重规则见 D6★：分组展开算，总计按会议去重

**验收标准**：
- [ ] 一个会议挂 AI 组和产品组 → 两个组的分组统计各计 1 次
- [ ] 同一个会议在「本季度总会议数」里只计 **1** 次
- [ ] 时长同理：分组各算，总计只加一次
- [ ] 取消的场次不计入；拒绝参会的人不计入他个人的参会次数

#### 6.5.3 导出 · P2

导出 CSV / Excel，供做季度汇报。

## 7. 非功能需求

| 项 | 要求 | 理由 |
|---|---|---|
| **隐私** | 忙闲接口**永不**返回标题/参与人/地点/材料 | D1 的底线；建议加接口级测试钉死 |
| **权限** | 判权只在后端；有效权限**唯一推导**仍在 `perm.rs` | 现有硬纪律，不能因为加了 item_grants 就散落 |
| **软删除** | 所有新增的读内容路径必须带 `deleted_at IS NULL` | 2026-08-06 审计教训，已写入 CLAUDE.md |
| **性能** | 忙闲查询 20 人 < 1s；月视图 < 500ms | 周期会议展开是主要开销，需要按时间窗裁剪 |
| **时区** | 存 IANA 名，不存偏移 | 6.1.5 已述 |
| **无 PVC** | 一切落 PG + Garage S3 | 平台硬约束 |
| **审计** | 会议增删改、应答、权限变更、归档全部入审计 | 会议信息会被用于绩效统计，可追溯是前提 |
| **可观测** | 周期展开失败、归档失败必须告警，不得静默降级 | 2026-08-06 教训：静默降级是最难查的故障 |

## 8. 数据模型草案

仅为评估工作量，详细设计在评审通过后做。

```sql
-- ── 项目(原 spaces,D0)────────────────────────────────
projects              -- 原 spaces 表
  id, name, description,
  visibility text NOT NULL DEFAULT 'public',  -- ★public / private(2026-08-06 由 team/personal 改名)★
                                         --   public  → 会议产生忙闲(仅忙/空),全平台可见
                                         --   private → 完全不占忙闲;★可多人(私下组队)★,随时可改
                                         --   ⚠ 只影响忙闲:两者的资料都只有成员能看
  owner text NOT NULL,                   -- ★唯一主持人(新增)★
  no_download bool, quota_bytes, ...     -- 沿用现有字段

project_members       -- 原 space_grants
  project_id, username, role,            -- admin(副手) / member / readonly(只读成员)
  added_by, added_at
  -- ⚠★绝不加「授权生效时间」字段★:那会把 D3 的「当前状态函数」退回「历史累积」,
  --   直接违反 R1「加入即可见全部历史」。
  -- ⚠★只到人,没有 grantee_type★:D12 删掉了「按组授权」,这张表里永远是具体用户名。

-- ★随 D12 删除★:groups / group_members 两张表整体去掉,
--   perm.rs 的 max(直接授权, 组授权) 简化为「查一次成员表」。

-- items 表新增一列(D10):
--   items.meeting_id  → 非空表示「这是某次会议的**只读区**文件夹或其中的材料」
--   ★只读★:不允许在此上传/改名/移动/删除,唯一写入口是会议详情页;
--   可做的只有 看/下载/复制到自由区/分享。复制出去的副本 meeting_id 置空(独立)。

-- ── 会议 ──────────────────────────────────────────
meetings
  id, title, description, organizer, group_id,
  starts_at, ends_at, timezone,          -- ★IANA 名,不存偏移★
  rrule text,                            -- NULL=单次;否则 RFC5545 规则
  rrule_until, status,                   -- status: 正常/已取消
  agenda text,                           -- ★议题与大致议程(D9:公开会议对所有人可见)★
  location text, online_url text,        -- 线下地点 / 线上链接(旁听者可见)
  visibility text NOT NULL DEFAULT 'private',   -- ★private / public(D9)★
  no_download bool, no_share bool,       -- 6.3.2 的两个开关
  created_at, updated_at

meeting_exceptions    -- 周期会议的「某一场特殊处理」
  meeting_id, occurrence_date,           -- 对应 RFC5545 的 RECURRENCE-ID
  action,                                -- 取消 / 改期 / 改链接
  new_starts_at, new_ends_at, new_online_url

meeting_participants  -- 参与关系
  meeting_id, username, role,            -- 发起人/必参/选参/★临时(D8)/旁听(D9)★
  status,                                -- 待定/接受/拒绝/建议改期
  counter_starts_at, counter_ends_at, counter_reason,   -- 建议改期
  responded_at
  -- ⚠ 这张表**不承载任何资料权限**(D3);它只管「谁被邀请了、答复是什么」

meeting_projects      -- 会议 × 项目(多对多,一次会可讨论多个项目)
  meeting_id, project_id, archive_folder_id

meeting_materials     -- 会议 × 内容(★纯索引,不是权限★,D7)
  meeting_id, item_id, phase,            -- 会前/会后
  uploaded_by, uploaded_at
  -- ★关联记 item_id★(D10):会议区只读,材料不会被搬走;

meeting_attendance    -- ★实际到场(会后补录,D11)★

  username text,                         -- 平台用户;旁听者也在这里
  display_name text,                     -- 无账号的外部人员只留姓名
  kind,                                  -- 参会 / 旁听
  recorded_by, recorded_at

meeting_durations     -- 时长与口径(D5)
  meeting_id, occurrence_date,
  seconds, source,                       -- 录制/手工/排程
  recorded_item_id                       -- 来自哪个录制文件

-- ★personal_events 表已删除★(v0.3):个人日程 = visibility='private' 的项目里的会议,

meeting_minutes       -- ★会议纪要(D14)★

  -- 模板字段(先只做一种通用模板,用不上的留空)
  topic, location, host, attendees, observers, absentees,
  agenda_text, content_md,               -- ★正文记录员写 Markdown★
  resolutions, todos, next_meeting_at,

meeting_messages      -- ★会议讨论区(D13)★
  id, meeting_id, sender,
  channel text NOT NULL,                 -- public / private
  peer text,                             -- private 时的对方(发起人或项目主持人)
```

**索引要点**：
- 忙闲查询是最热路径，`(username, starts_at, ends_at)` 必须有覆盖索引
- 周期会议无法靠索引裁剪，需在应用层按时间窗展开后再合并
- 时间线入口按 `meeting_participants(username) × meetings(starts_at DESC)` 查，注意加复合索引

## 9. 分期计划

一次做完风险太大（日历本身就是个大工程）。建议五期，**每期都能独立上线并产生价值**：

| 期 | 内容 | 产出的价值 | 粗估 |
|---|---|---|---|
| **M1** | 项目（团队/个人、成员两档、**批量加人**、owner 转移）+ 单次会议（**必关联项目**、**记录员必填**）+ **会议详情页** + 忙闲（**个人项目隐形 + 私事冲突提醒本人**）+ 应答四态 + 个人日历 | **能把会约成并如期开上** | 最大的一块 |
| **M2** | 建议改期协商 + ★**讨论区（公开+私聊）**★ + 周期性会议 + 公开会议与旁听 + 移出成员 | 撞车能协商，私事也有出口 | 中 |
| **M3** | 会前/会后材料 + 自动转写**参考稿** + ★**记录员按模板写纪要**★（草稿/完成）+ 只读会议区 | 材料集中，纪要有人负责 | 中（大量复用现有能力） |
| **M4** | ★**LaTeX → PDF**★ + 时间线入口 + 复制到自由区 + 分享（**含收紧时撤旧链接**）+ 材料权限开关 | 出得了正式文件，找得到、发得出去 | 中（PDF 依赖平台服务） |
| **M5** | 统计（个人/项目/去重/口径来源）+ ★**搜索**★ + 纪要催办 | 季度汇报有数据，历史查得到 | 中 |

★**M1 必须含「会议详情页」**★——这是[故事地图](./STORY-MAP.md)查出来的分期断点：
原本把它排在 M3，但没有它，M1 约完会**看不到线上链接**，到点了不知道去哪开，流程断在「去开会」这一步。
M1 版的详情页只有信息（时间/议程/链接/应答情况），**不显示材料区**（材料区随 M3 出现）。

**为什么这个顺序**：M1 独立可用（哪怕后面都不做，也解决了最痛的排会问题）；M3 大量复用现有
上传/转写能力，性价比最高；M5 依赖数据积累，放最后最合理——**没有数据的统计页是空的**。
每一期的「能不能走通」自检见[故事地图 §4](./STORY-MAP.md)。

⚠ **D0 + D3 + D12 三条一起改动权限推导与表结构**，这是全系统最敏感的地方，
必须在 M1 一次做完（不留兼容层），并配单独的安全评审 + 回归测试。

✅ **M4 的 PDF 依赖的共享 LaTeX 服务，平台已立项**（D15，#119）——congrove **镜像不用动**，
只提交 tex。原先"可能要多一轮装 TeX 集"的排期预留**可以取消**。
剩余依赖：等平台同步调用地址与字体清单。

## 10. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| **周期会议 + 时区 + 例外是经典泥潭** | RFC 5545 光递归规则就几十页 | 用成熟 Rust RRULE 库，别自己写；单测覆盖月末/年末/闰年 |
| **忙闲泄露隐私** | 违反 D1 承诺，信任崩塌 | 接口级测试钉死返回字段；代码评审重点盯 |
| **item_grants 引入权限旁路** | 越权访问 | 权限推导保持唯一入口；上线前专项审计 |
| **统计口径争议** | 数字被质疑，功能失去意义 | D5 的「显示来源」；统计规则文档化并让用户确认 |
| **范围膨胀** | 做不完 | 第 1.3 节的「不做」清单要守住；OA 是个无底洞 |
| **和现有功能的交互** | 回归 | 归档走现有 items，必然触及软删除/配额/分享，需回归测试 |
| ★**spaces → projects 是破坏性重构**★ | 表名/API/前端全涉及 | **趁线上数据近乎为零的现在做**；一次性改完，不留兼容层（留了就是永久的两套概念） |
| ★**公开分享是 R1 的后门**★ | 离开项目的人凭旧链接仍可访问 | 移出成员时连带撤销其公开链接（D3 硬要求 1）；上线前专项验证 |
| **删除小组后加人变繁琐** | 每年新人逐个加，体验差 | 成员管理页**必须**支持多选批量加入（放 M1，别延后） |
| **临时参会人被误当成员** | 越权看到材料 | D8 的边界要有接口级测试：临时参会人取任何材料一律 404 |
