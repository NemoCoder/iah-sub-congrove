## 1. 背景：★后端早就有了,一直没有界面★

盘点 `src/http/admin.rs` 的结论,是这个需求真正的形状 —— **它主要不是「缺功能」,是「缺一页界面」**：

| API | 后端 | 界面 |
|---|---|---|
| `GET /admin/users` 用户列表 | ✅ 早就有 | ❌ **没有** |
| `PUT /admin/users/{u}/super` 授/撤超管 | ✅ 早就有（含「不能撤最后一个超管」防锁死） | ❌ **没有** |
| `PUT /admin/users/{u}/quota` 调配额 | ✅ 早就有 | ❌ **没有** |
| `GET /admin/audit` 全局审计 | ✅ 早就有 | ❌ **没有** |
| `GET/PUT /admin/llm/model` AI 模型 | ✅ 2026-08-16 热修加的 | ✅ 有（塞在「开发者」页） |

⚠ 这本身是个值得记下来的教训：**四个带 `require_super` 的写接口,在没有任何界面的情况下活了很久**。
它们不是死代码（curl 调得通、审计也记）,但**没有人能在界面上看见自己有这些权力** ——
于是「谁是超管」「谁的配额被谁改成了多少」这些问题,一直只能进数据库查。

## 2. 目标

1. 超管能在**界面上**看到并管理用户：谁是超管、谁多少配额、最近有谁登录过。
2. 超管能在**界面上**查全局审计,不必进库。
3. 把三项**治理决策**从 env / 硬编码里搬出来 —— 它们是「产品负责人的决定」,不该是「运维的部署动作」。

## 3. 非目标（★这轮明确不做★）

- **不做 ASR 模型 / 说话人分离的配置**（liaoruili 2026-08-16 选范围时排除）。
- **不做超管模式时长（2h）、活动最长跨度（30 天）的配置**（同上）。
- **不做用户的创建/删除**。用户由 Keycloak SSO 落地,congrove 只在人登录时把他记进 `app_user`;
  在这里「删用户」会造出一个 SSO 还认、congrove 不认的幽灵状态。
- **★不做用户列表的前缀搜索/模糊筛★** —— 这一页列的是**全体登录过的用户**,本身就是名册,
  超管看得见是应当的;但**不要**把它做成一个能被复用的搜索接口。
  （平台侧 2026-08-07 liaoruili 拍过板：不做用户 list/search 接口,前缀搜索 = 目录枚举。
  这里的 `/admin/users` 挂在 `require_super` 后面,和那条规矩不冲突,但**别把它挪到 super 之外**。）
- **不动凭证类配置**（DB / OIDC / S3 / 网关 key）。它们进不了界面,理由不是麻烦,是
  **一个能在界面上改数据库连接串的后台,等于把整个系统的钥匙挂在一个 XSS 上**。

## 4. 角色

只有一种：**超管,且处于超管模式**（`is_super`,见 `TECH-DESIGN-admin-mode.md`）。
入口按「资格」(`can_super`) 显示、按「特权」(`is_super`) 生效 —— 沿用 2026-08-09 定的三条之一
「入口留着,点了提示开启」,不新造规矩。

## 5. 功能范围

### 5.1 用户管理

一张表,列：用户名 / 姓名 / 邮箱 / 超管 / 配额 / 首次登录 / 最近登录。行内两个动作：

- **授 / 撤超管**（`PUT .../super`）
- **改配额**（`PUT .../quota`）

已知的两条边界,界面必须说清楚,否则人会以为系统坏了：

1. ★**不能撤掉最后一个超管**★ —— 后端已拒,界面要在按钮上先说,别让人撞了才知道。
2. ★**env 白名单里的用户,撤了会在下次登录时复活**★ —— 后端注释写着
   「白名单用户(env 种子)由登录逻辑重新置回,撤了也会复活」。
   ⚠ 这是**最容易被当成 bug 的一条**：撤销成功、界面刷新也确实撤了,人走开、第二天他又是超管。
   界面必须**在撤销前**就说明白,而不是事后。

### 5.2 全局审计

一张表：时间 / 操作人 / 动作 / 对象 / 详情。后端现在只支持 `limit`（默认 200,封顶 2000）。

### 5.3 治理配置（三项）

| 项 | 现在在哪 | 改成 |
|---|---|---|
| **谁能建项目** | env `CONGROVE_PROJECT_CREATORS`（逗号分隔用户名;非空时仅名单内 + 超管可建） | 库里可改,env 兜底 |
| **新用户默认配额** | ★写死★ `config.rs: DEFAULT_QUOTA_BYTES = 10 GiB` | 库里可改,常量兜底 |
| **全站默认提醒提前量** | ★写死★ `remind.rs: DEFAULT_REMIND_MIN = 15` | 库里可改,常量兜底 |

**取值一律照 AI 模型那套「唯一推导」**：`库 > env > 编译期默认`,
且★只有一个函数能推导它★ —— 别在别处直接读常量或 `state.config`,
那样超管改了不生效,**而且它不报错,只是安静地继续用老值**（`effective_llm_model` 的头注已经写了这条,
这三项照抄同一形状）。

## 6. 关键决策（记「为什么」）

**D1. 新开「后台」页,把 AI 模型卡片从「开发者」页挪过来。**
现在 AI 模型卡片住在 `apidoc-view.tsx`（「开发者」页）—— 那页本来是给人看 API 文档的,
一个**会改全站行为的开关**混在文档里,既不好找,也让「开发者」这个入口名不副实。
⚠ 挪动 = 老位置消失,已经习惯在那儿改模型的人（就你一个）要知道。

**D2. 治理配置沿用 `app_setting` 这张 kv 表,不为三个配置项各开一张表。**
`0002_app_setting.sql` 已经建好（`key` / `value` / `updated_by` / `updated_at`）,
AI 模型就存在里面。三项都是「一个值 + 谁改的 + 什么时候」,kv 正好。

**D3. 每一次改都进审计。** 后端 `set_super` / `set_quota` 已经在记（`admin.quota` 等）;
三项治理配置的写入也要记 —— **这一页上的每个动作都是「权/供给」类**,
按 CODE-QUALITY 的规矩,它们既要审计也要测试。

**D4. 配额那一列先只显示「额度」,不显示「已用」。**
`UserRow` 现在没有配额字段,得补;但「已用」要跨 `items` 求和,是另一个量级的查询。
个人面板已有 `/api/me/quota` 给本人看已用。⇒ 这轮先把**额度**显示出来并可改;
「已用」列作为后续可选项,不进这轮。

## 7. 需求确认（相位 2）：★开放问题已全部关闭★

2026-08-16 逐条问过 liaoruili,原样记在这里 —— **这是相位 2 的硬闸,过了才进相位 4**：

| # | 问题 | 结论 | 谁定的 |
|---|---|---|---|
| Q1 | 「后台」页怎么摆? | ★**新开「后台」,与「开发者」并列**★。两件事：后台=改系统、开发者=看文档。AI 模型卡片从「开发者」页**挪到后台** | liaoruili |
| Q2 | 建项目白名单怎么填? | ★**从用户列表里勾**★,不用自由文本 | liaoruili |
| Q3 | 白名单**空**算什么? | ★**空 = 人人可建（维持现状）**★,但界面上要把这句话写出来 | liaoruili |
| Q4 | 改「新用户默认配额」影响存量用户吗? | **不影响** —— 这不是选择,是代码现状：它只在建 `user_quota` 那一刻用一次(`items.rs:169`) | 代码事实 |
| Q5 | 审计要不要按人/动作/时间筛? | ★**这轮不做**★,只 limit + 前端本地过滤 | liaoruili |

**Q2 的理由值得单独记下**（它是这一页最容易埋雷的地方）：
手输用户名会打错,而★打错的后果是「这个人从此建不了项目」,并且**没有任何地方会报错**★ ——
白名单是个字符串比对,名字对不上就是不在名单里,系统不会说「你填的这个人不存在」。
**安静地错**,而且要等到那个人某天想建项目才暴露。从已有的用户表里勾,这一整类错就不存在了。

**Q3 的理由**：改成「空 = 只有超管能建」是一次★静默的权限收紧★ ——
升级部署的同一刻,现在能建项目的人全部失去这个能力,而没有人会收到通知。
维持现状 + **在界面上写清楚现在是哪种状态**,比换一个「更安全的默认」要安全。
