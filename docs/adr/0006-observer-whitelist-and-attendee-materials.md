# ADR-0006：旁听看不到内容（白名单 + 单点否决）；参会人对材料有完整读写权

**状态**：已定（liaoruili 2026-08-16 逐条拍板） · **性质**：★「权」路径★ · **它推翻 D8**

## 背景：liaoruili 撞到的那个半截状态

> 「现在你给人家看到材料又上传不了」

查下来是**两套判据不同源**：

- **前端**按「是不是参会人」画材料卡片（`d.participants && <MaterialsCard/>`）；
- **后端**按「是不是关联项目的成员」判权（`activity_items` 的 D8 注释：「材料按项目成员身份判权，不是按参会身份」）。

⇒ 一个「参会人但不是项目成员」的人：★卡片在、列表空（403）、上传失败★。
★根因不是权限判错（后端拒得对），是前端拿「是不是参会人」当了「能不能看材料」的替身判据。★

顺着查还发现两处**方向相反**的缺口，都在下面一并定掉。

## 决定一：★旁听 = 白名单，且是对内容的**单点否决**★

旁听者只知道「这场活动是什么、在哪、什么时候、谁攒的」，不接触活动的任何内容产出。

| 旁听**能**看 | 旁听**不能**看 |
|---|---|
| 标题、议程、时间、地点 | 材料 |
| 发起人 | 录制 |
| 线上地址 / 会议号 | 纪要 |
| | 讨论 |
| | 参会人 —— ★连人数都不给★ |

「连人数都不给」是 liaoruili 明确选的：**人数本身也是信息**（「这会只有 2 个人」就足够说明性质）。

★**旁听身份压过项目成员身份**★ —— 这是本 ADR 最要紧的一条。
现在 `activity_items` 只问「你是不是关联项目的成员」，于是**一个恰好是项目成员的人，以旁听身份进来，
API 直接拿得到材料和录制**（界面上看不到只是因为前端另有一道 `d.participants` 判断 ——
★而那不是安全边界★）。

⇒ 判定必须是：**先问是不是旁听，是就否决**，再谈别的身份。和 ADR-0005 的材料区隔离同一个形状。

### 顺带补两个反方向的缺口

| | 现状 | 改成 |
|---|---|---|
| 发起人 | ★后端把 `organizer` 置成空串★（`activities.rs` 的 Observer 分支）—— 界面上那行是空的 | 如实给 |
| 线上地址 | `OnlineCard` 被 `m.online_url && d.participants` 挡着 —— 旁听拿得到 `online_url` 却没地方显示 | 旁听也显示（**只显示地址本身，不给「改动历史」**——那是活动内部的过程信息） |

## 决定二：★参会人（非项目成员）对这场活动的材料有完整读写权★ —— 推翻 D8

D8 原话是「材料按项目成员身份判权，不是按参会身份；临时参会人看得到活动，看不到材料」。
**这一条从今天起不成立**，理由是 liaoruili 定的产品判断：

> ★「开会带材料」是这个产品的核心场景★ —— 参会人手里的 PPT、数据、录音正是活动材料的**主要来源**。
> 堵住它，发起人就得当人肉中转：别人发给他、他再传一遍。**那是把系统该干的活推回给人。**

| 动作 | 参会人（非项目成员） |
|---|---|
| 看 / 下载这场活动的材料与录制 | ✅（活动或项目开了禁下载则照挡） |
| 上传材料 | ✅ |
| ★上传录制★ | ✅（liaoruili 选了「放开」） |
| 改名 / 删除**自己传的** | ✅ |
| 改名 / 删除**别人传的** | ❌ |
| 项目树里其他任何东西 | ❌（不变） |

**边界收在「这场活动」，不是「这个项目」** —— ★参会人是被请进这一间会议室，不是拿到了整栋楼的钥匙。★

### 三条已有机制让这个放开是安全的（不需要新设计）

1. ★配额算的是**项目 owner**，不是上传者★（`items.rs::project_owner`：「额度算 owner 的，不算操作者的」）。
   所以「非成员传东西会占谁的额度」这个顾虑早有答案：**占召集人的**，而那正是他召集这场会该承担的。
2. 落点由后端算，前端给不了任意 `project_id` —— 上传只能落到**这场活动的材料文件夹**。
3. 禁下载 / 禁分享是**活动级策略**，对所有角色生效，不受本 ADR 影响。

### ⚠ 放开录制的代价，写清楚

录制**会自动触发转写**（GPU + LLM 预算），而且它是「活动时长」的判据来源（D5）。
⇒ 一个参会人传一段无关的长视频，既烧预算又把活动时长算歪。

liaoruili 知道这一点仍选了放开（一致、少一条要解释的规则）。★这条代价记在这里，
真出现「有人传垃圾录像烧预算」时，回来看这一段，别当成没想到过。★

## 决定三：录制 / 材料要能点开看

活动详情里材料与录制的「名称」列现在是**纯文本**，点不开。
而 `openViewer(id)` + `<VideoPlayer standalone>` **早就有**（项目树里就在用，viewer 页对
`kind === 'video'` 直接播、支持 Range 拖动）。

⇒ ★又是「能力早就有、这里没入口」★（和超管后台那四个 API 是同一个形状）。名称列改成可点，
点开走同一个 viewer —— 视频直接播，PDF / 图片 / 文本各按既有预览走。

## 实现上必须守住的两条

**① 判定进 `activity_view` / 一个新的单点推导，不要在 4 个 handler 里各写各的。**
现在 `activity_items` / `rename_activity_item` / `delete_activity_item` / 上传落点各判各的，
★这正是「前端一套后端一套」那个 bug 的成因的放大版★。

**② 前端不许再用「是不是参会人」当「能不能看材料」的替身。**
后端在 detail 里如实给一个 `can_see_items`（以及 `can_upload_items`），前端照着画。
判据只有一处，**新增入口自动被覆盖** —— 和 ADR-0005「单点否决」同一条理由。

## 推翻它的条件

- 若将来出现「参会人往材料区倒垃圾 / 烧转写预算」的真实事件 → 回到「录制只有发起人+记录员能传」
  （那是 liaoruili 当时没选的选项，理由都记在上面，不必重新论证）。
- 若产品上出现「旁听也要看会议纪要」的场景（例如公开讲座的公开纪要）→ 那应当是**活动级的显式开关**，
  不是把旁听的白名单放宽 —— ★白名单一旦开始按情况放宽，它就不再是白名单。★
