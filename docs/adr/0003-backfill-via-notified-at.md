# ADR-0003：「补录」判据存 `notified_at` 事实，不用生成列推导

**状态**：已定（PRD L0b 已回填，liaoruili 2026-08-08） · **实施**：M0-2

## 决定

「这条活动是不是补录的」**存一个事实**：`activity_participants.notified_at`
（这个人有没有被通知过、什么时候）。**不设生成列**、不靠 `created_at` 与 `starts_at` 现算。

## 为什么原判据是错的

原判据 `created_at > starts_at`（「建的时候会已经开完了 = 补录」）**会随改期翻转**：

- 建一场未来的会 → 不是补录；
- 把它改到昨天 → 判据翻成「是补录」，**而那个人早就被通知过、也确实参加了**。

★缺陷在判据本身，不在实现方式★ —— 即使按 PRD 要求「现算不存」，一样会翻转。
实测还发现生成列在 `INSERT` 与 `UPDATE` 两条路径上给出的值不同（false / true），
那是同一个病的另一个症状。

**存事实就没有这个问题**：通知过就是通知过，改期不会让历史消失。

## 连带写死的两条残留边界

1. **补录→改到未来**：要**补发邀请并置位** `notified_at`。不补发的话，那个人对这场活动
   自始至终不知情，却已经出现在他的日程里。
2. **统计口径收紧成只认 `accepted`**：原来是 `status <> 'declined'`，于是
   「建未来的会拉上张三 → 他被通知一次 → 改成昨天 9:00–18:00」**两步就能给他的季度统计塞 9 小时**。

## 流程上的一条教训（留着）

原判据是 PRD L0b 写的，而 **PRD 是相位 2 的门禁产物、liaoruili 签过字**。
技术设计**换掉了它**（换得对），但按 SDLC，★需求类判据不能由技术设计自行改写★ ——
必须回到相位 0 让产品负责人拍板、回填 PRD。这次是这么做的。

## 不管什么

不管「谁改的期」这类审计维度（`audit_log` 已有）；不管补录 UI（M1 范围）。
